# evalcore — зона Verwelius

Стык следующей итерации: C01_CONTRACT_HANDOFF.
`timing_contract.py` и `iteration_contract.py` содержат dataclasses/Protocol для V-01…V-03
и C-05, без runtime-зависимостей и без реализации новых алгоритмов. Старые models.py,
scoring/criteria и результаты остаются прежними. Общие 24 примера времени —
`contracts/examples/timing-v2.json`, методика — `contracts/I-TIME.md`.

Этап 3 C-01: `iteration_contract.PredictionContext` и `SessionPredictor` закрепляют
`predict_for_session(trainee, scenario, *, context) -> Prediction` для V-03.
Контекст содержит UUID snapshot и TimingPolicy; история CalibrationObservation —
собственный норматив и качество времени, с null для неизвестных сведений.
Точное отображение C-06 — [контракт](../../contracts/evalcore.md). Новый алгоритм
не реализован и не подключён к scheduler; старый predict/fallback сохранён.

V-03 предоставляет `adaptive.recommend_level(current_level, history, *,
critical_flags_by_card)`. Правиловая версия использует до пяти последних завершённых попыток,
effective-балл с override, только подтверждённые измерения времени и критические флаги. До трёх
попыток возвращается `keep` с явной пометкой холодного старта. После этого средний балл ≥0,8 без
критических ошибок и превышений повышает сложность на один шаг; средний балл <0,6, две попытки
с критическими ошибками или большинство подтверждённых превышений понижает её. API/C-06
собирает историю и подключает результат к отчёту отдельно.

Чистый Python 3.12, без FastAPI/БД/ML/HTTP. Runtime-зависимостей нет.
Из корня: `uv sync --all-packages`, `uv run pytest packages/evalcore/tests`.
Из этой папки: `uv sync`, `uv run pytest tests` (uv найдёт общий workspace и lock).

Входной контракт: `../../contracts/evalcore.md`, `scenario.schema.json`, `data_formats.md`.
`models.py` фиксирует EvalContext, CriterionResult, Evaluation, Trainee, Prediction, Criterion.
Оркестрация `evaluate(ctx)` уже реализована: она проверяет настройки, вызывает критерии
в стабильном порядке и передаёт результаты в проверенную взвешенную агрегацию с critical cap.
Все семь критериев T-006 реализованы и зарегистрированы. 28.09 добавлены критерии комментария
`spelling` и `comment_keywords` (`comment.py`, отдельный реестр `COMMENT_REGISTRY`): вес
необязателен — без него критерий не считается, итоги старых занятий прежние. Словаря в
evalcore нет: проверку текста передают через `EvalContext.text_checker` (протокол

по-прежнему нет. `predict(trainee, scenario)` остаётся

08.10 (DT-10) добавлен критерий `brigade_work` «Работа с бригадой» (`brigade.py`, реестр
`BRIGADE_REGISTRY`): реакция на события бригады из `EvalContext.scenario_events` — уточнение,

[контракт](../../contracts/evalcore.md#работа-с-бригадой-dt-10-0810).

12.10 (DT-16) — ответ бригаде голосом (`voice_reply.py`): `voice_reply_option` сводит
распознанную фразу к варианту ответа реплики (значимые слова подписи по начальной форме, все её
числа; для поправки адреса — улица, её тип и дом без исправления опечаток, «Бескудниковский
переулок» не проходит за бульвар), `reply_hints` — подсказки распознаванию. В `evidence`
`brigade_work` — «голосом» / «вариантом», громкость и число несопоставленных фраз.

Первая задача **T-006**: семь критериев из `defaults.CRITERIA`, evidence и explanation на русском,
реестр `criteria.REGISTRY`, score 0..1; формула `raw = Σ(w*s)/Σw`, при critical —
`total = raw * critical_cap` из settings (без critical: `total = raw`). Так критическая
ошибка не даёт зачёт, но попытки с одной ошибкой и несколькими потерями баллов не
склеиваются в одинаковые 50 %. Уже сохранённые оценки не пересчитываются.
Критерий с весом 0 не влияет ни на среднее, ни на список критических ошибок.
Реестр, семь критериев, валидация весов/баллов и формула реализованы.
Нулевую сумму весов следует отвергать явно. Алгоритм и формулы подтверждаются тестами.

Методика T-006 v0:

- `reaction_time`: первое `deliver` → первое `open`; `1` при `t≤N`, иначе
  `max(0, 2-t/N)`. Нет события или нарушена хронология — `0`.
- `handling_time`: первое `open` → первое терминальное действие (`completed`, `refused`,
  `rejected`, `redirect`); та же линейная формула.
- `status_flow`: `LCS(expected, actual) / max(len(expected), len(actual))`; `deliver` означает
  `received`, событие `redirect` — состояние `redirected`, служебное `added` не оценивается.
  Статус, чьи доклады-основания (`planned_messages[].justifies_state`) не были предъявлены
  обучаемому, убирается из эталона и из факта (L-01, `contracts/evalcore.md`).
- `routing`: цепочка решений `accepted`/`rejected`/`redirected` должна совпасть с эталоном;
  после отказа проверяется конечное перенаправление и его `service_id`. Пропущенное
  перенаправление и неверный адресат дают критический ноль. Исправление A1 от 23.09.
- `required_fields`: доля верно заполненных полей из `reference.required_fields`; «Номер наряда» сверяется по цифрам с прямыми номерами бригад карточки (`EvalContext.brigade_numbers`), без бригад — только непустота.
- `address` (DT-14, 08.10): адрес диспетчер ДДС не вводит, критерий ищет его во всех
  комментариях к статусам. Адрес карточки совпадает с `expected_address` — адрес в комментарии
  можно не писать, ошибка только искажённый адрес (другая улица, другой номер дома, корпуса,
  квартиры). Адрес уточнён (`address_clarified`: эталон отличается от адреса карточки) — улица,
  дом и непустые корпус, квартира должны быть в комментарии; город — если уточнился и он.
  Балл — доля компонентов эталона без ошибки; ошибка улицы или дома — critical. Ручной
  `current.address` старых попыток сравнивается по полям, как раньше.
- `call`: лучший звонок получает равные доли за успешное соединение, правильного адресата
  (`service_id` и `phone_ext` вместе) и время начала после `deliver`. Временная доля равна `1`
  до `before_s`, затем линейно снижается до `0` ещё за `before_s`. Отсутствие обязательного
  звонка, ответа или правильного адресата — critical. Если `required=false`, критерий равен `1`.
  Прямой номер направленной бригады той же службы — правильный адресат; входящий вызов
  бригады (`direction=inbound`) обязательным не считается (28.09). Звонок бригаде, которая
  не была направлена на происшествие (`refusal`), — неверный адресат: бригада отказала,
  информацию никто не принял. Отдельного штрафа нет: балл берётся по лучшему звонку, а число
  таких звонков дописывается в `evidence` для преподавателя.
  Доклад службе (DT-05, `call_hangup.report_choices` / `report_modes`): доля «соединение»
  засчитывается только за полный доклад — голосом `1`, вариантом ответа
  `settings.report_choice_factor` (по умолчанию `0,5`, `defaults.REPORT_CHOICE_FACTOR`).
  Доклад строится по порядку памятки ДДС, с. 32 (DT-11, `criteria.REPORT_PARTS`): кто вы,
  адрес и повод, карточка, что изменилось. Голосовой текст сводится к частям в
  `report.voice_report_parts` (сравнение слов по начальной форме, как у ключевых сведений
  комментария; адрес — улица и дом без исправления опечаток, карточка — слово или номер), вид
  доклада — первая недостающая часть (`no_who`, `no_address`, `no_card`, `no_change`), иначе
  `full`. Части каждого доклада — в `call_hangup.report_parts`; нет поля (варианты ответа, отбои
  до 08.10.2026) — части по виду (`criteria.report_parts_of`, старые `no_incident` и
  `no_victims` — без «адреса и повода» и без «что изменилось»). В `evidence`: «голосом» /
  «ответ вариантом», число нераспознанных фраз и строка «Части доклада службе … по памятке
  ДДС, с. 32: кто вы ✓, адрес и повод ✓, карточка ✗, что изменилось ✓» — по первому докладу
  звонка, то есть по тому, что обучаемый сказал до уточнений службы. Карточка обязательна и
  показывается только в звонке в 112 (`criteria.required_parts`): так требует памятка; в
  звонках руководителю, должностным лицам и другим службам доклад полный и без неё.

V-01: `evaluate(ctx, timing=result)` принимает общий `TimingResult` из `calculate_timing`.
Для v3 `reaction_time` использует направление → первый первичный статус, а `handling_time` —
активную обработку без подтверждённого ожидания. Для v1/v2 берётся полная обработка;
`evaluate(ctx)` без нового аргумента сохраняет прежнюю legacy-семантику. Нормативы читаются
из снимка в `TimingResult`, а evidence сообщает версию, качество, источники и аномалии времени.

`routing` v0 проверяет решение против `reference`, потому что в `EvalContext` нет идентификатора
ДДС текущего обучаемого; интерпретатор условий классификатора входит в T-026.

Интерпретационное замечание: `reaction_time` показывает соблюдение норматива реакции, а не
вероятность успешной помощи. Если в будущем оценка будет калиброваться по фактическим исходам,
имеет смысл отдельно рассмотреть время от `deliver` до первого эффективного действия. Это
позволит не штрафовать одну и ту же задержку одновременно через реакцию и последующую обработку.

Замечание о временной шкале: текущая формула для `reaction_time` и `handling_time` эквивалентна
`score = max(0, 1 - (t-N)/G)` при `G=N`. Здесь `N` — граница норматива, а `G` — интервал после
нарушения, за который балл снижается от `1` до `0`. При дальнейшем уточнении методики эти величины
можно разделить: норматив отвечает за начало нарушения, а отдельный `G` — за строгость штрафа.
Это особенно существенно для обработки: значение `N=180` само по себе не доказывает, что балл
должен снижаться до нуля ещё в течение следующих 180 секунд.

V-02 проверял структурированный ручной адрес из `current.address`; с 08.10 (DT-14) поле ввода
из АРМ ДДС убрано, и это сравнение остаётся только для старых попыток. Регистр, `ё/е`,
пунктуация и сокращения `г.`, `ул.`, `д.`, `корп.`, `кв.` нормализуются; остальные компоненты
сравниваются точно, поэтому похожая другая улица не становится правильной.

Адрес в комментарии (`address.other_street`): другая улица — слово с заглавной буквы рядом с
типом улицы («ул. Тверская», «Тверская улица») или слово, отличающееся от названия эталона на
одну букву (в названии от 8 букв — на две) при той же первой букве: «Дубининская» при
«Дубнинская». То же слово в другом падеже («на Дубнинской улице») — та же улица. «Проезд» и
«площадь» типом улицы здесь не считаются: «проезд затруднён», «площадь пожара» — не адрес.
Ключевые сведения комментария (`comment_keywords`) требуют адрес только уточнённый.
Латинские буквы-двойники в русских словах («Тверскaя» с латинской «a») перед сверкой
становятся русскими (`address.cyrillic_twins`); слово целиком латиницей не меняется.

16.10 (TC-10) — замечания разбора (`remarks.py`, `CriterionResult.remarks`): у каждой ошибки
критерия — что не так, цитата сказанного или написанного (±45 символов, без регистра, «ё» и
двойников), последствие в мире, страница памятки ДДС и «Повторите: …». Статус меньше чем через
`CLICKTHROUGH_S` после открытия карточки или прошлого статуса — замечание «карточку не читали»
без снижения балла. Ошибка данных сценария — «вопрос к данным», балл не снижает. Суть
происшествия и пострадавшие засчитываются и словами описания карточки (половина значимых
слов). Эталонное прохождение каждого сценария `data/scenarios` — без замечаний
(`apps/api/tests/test_reference_runs.py`). Формулы — [контракт](../../contracts/evalcore.md).

Golden лежат в `../../data/golden_scenarios/`: scenario + current + events + calls + settings
+ expected (criteria/total/tolerance). Конструируйте EvalContext только из соответствующих полей.
Pytest включает unit-, ошибочные, граничные и golden-тесты оценщика. Цель T-006 — ≥80 %
покрытия реализованного оценщика.

`classifier.py` передаётся во владение Verwelius после D1. Он сохраняет условия колонок,
а не решает маршрутизацию по всем колонкам сразу. Скрипт сборки — зона капитана.
