## Действующий транспорт

Источник машинных типов: `components.schemas.WsServerEvent` и `WsClientEvent` в OpenAPI.
Пример: `contracts/examples/ws.json`. Один WebSocket `/ws` с JWT-cookie; origin должен
совпадать с текущим приложением. Обучаемый получает только собственные карточки.

Конверт сервера: `{schema_version: 1, event_id: UUID, server_ts: ISO-UTC, type, payload}`.

| type | payload | Потребитель |
|---|---|---|
| `snapshot` | `{cards: Card[], sessions: Session[], evaluations: Evaluation[]}` | shared: начальная синхронизация и reconnect |
| `presence` | `{user_id, online}` | live-доска; молчание сокета > 45 с и стартовый список для преподавателя — [live-lesson.md](live-lesson.md) |
| `card.appeared`, `card.updated` | `Card` | АРМ и live-доска |
| `session.started`, `session.finished` | `Session` | АРМ и пульт |
| `evaluation.partial`, `evaluation.complete` | `Evaluation` | результаты и пульт |
| `call.state` | `Call` | софтфон и live-доска |
| `clock.pong` | `{client_ts}` | shared, оценка разницы часов |

Клиент отправляет только `{type: 'clock.ping', client_ts: ISO-UTC}`.
Сервер возвращает этот timestamp и собственный `server_ts`.
`offset_ms = server_ts - (sent_client_ts + received_client_ts)/2`.
Пинг повторяется каждые 5 с. Оффсет служит для отображения таймеров; исходный `client_ts`
не переписывается. В рабочем backend оценка оффсета и RTT записывается отдельно (T-008).
В моке сохранённый `clock_offset_ms = 0` — это заглушка, не готовая оценка времени.

Действия идут **HTTP POST `/cards/{id}/events`**, а WS разносит подтверждённые изменения.
`client_event_id` создаётся один раз **до** записи в IndexedDB; UUID и timestamp неизменны при retry.
При потере ответа событие отправляется повторно; ответ содержит `duplicate: true`.
Повтор того же UUID с другим телом/карточкой → 409. Idempotency-key scoped по actor_id.

Повтор действия новым UUID (TC-08, двойной щелчок по «Подтвердить»): второй `status_change` или
`redirect`, который не меняет карточку, потому что она уже в этом состоянии от такого же
действия того же автора с тем же телом (`state` и `comment`; для `redirect` — `service_id` и
`comment`), сервер подтверждает как `duplicate: true` и новой записи в `card_events` не создаёт:
ключ повтора — карточка, автор, вид и тело действия. Событие с другим телом (другой комментарий)
по-прежнему получает 409 «Недопустимый переход», очередь клиента сохраняет его как отказ.

Очередь принадлежит `shared/ws/`, отделена по user_id, сохраняет порядок внутри
`(user_id, card_id)`. 2xx удаляет только подтверждённый элемент. Сеть/5xx/401
останавливают текущую отправку до восстановления, без записи постоянного failure.
Остальные отказы сохраняются с `failure` и останавливают следующие события **этой
карточки**; независимые карточки того же пользователя продолжают отправляться.
Отказ и зависимые события остаются в IndexedDB после retry/reload с исходными
UUID, timestamps, payload и sequence. Автоматического удаления, признания успехом
или повторной отправки постоянного отказа нет; требуется разбор через Outbox.list()
и PendingActions. Существующая структура IndexedDB v2 сохраняется без новой миграции.
Переподключение: 0.5 → 1 → 2 → 4 → 5 с, затем snapshot и HTTP-refresh.
Обрыв связи видит и обучаемый (TC-08): клиент `shared/ws` отдаёт состояние связи
(`online`, момент следующей попытки, число ждущих действий) и команду «Повторить сейчас».
Состояние «нет связи» — закрытый WS или отказ сети при отправке очереди; браузерные события
`offline`/`online` его только ускоряют. Пока связи нет, действия остаются в IndexedDB и
уходят по `sequence`, как до обрыва; строку о потере связи показывает зона «Тренажёр».
В database-режиме API восстанавливает PostgreSQL LISTEN с теми же задержками
после стартовой ошибки или обрыва. Подключение, запросы и закрытие ограничены
5 с; проверка соединения каждые 5 с обнаруживает потерю транспорта без уведомления.
После успешной подписки API закрывает прежние WS с кодом 1012: браузер автоматически
переподключается, повторно проходит авторизацию и получает snapshot по текущим правам.
Это необходимо, поскольку NOTIFY не хранит события за время разрыва. Пропущенные
уведомления не воспроизводятся как новые события; состояние перечитывается из БД.
HTTP `/health` сохраняет прежние поля и код 200; общий `status` становится `degraded`,
пока LISTEN не готов, даже при `database: ok` и `worker: ok`. Compose healthcheck
сохраняет проверку доступности HTTP; готовность уведомлений видна в теле Health.
Snapshot означает замену отображаемого состояния, а не появление новой карточки.
Показ новой строки подтверждается `deliver` **после рендера** и получения состояния
её занятия через GET `/sessions/{id}`. Пока состояние неизвестно/недоступно или
занятие не running, АРМ не создаёт deliver/open, правки, переходы, redirect и события
звонков. Reload перечитывает состояние; session.started/session.finished обновляют
контекст карточки, snapshot инвалидирует его для HTTP-refresh.
Просмотр карточки и истории остаётся доступным. Завершение занятия останавливает
локальные таймеры/звук/запись софтфона без новых call-событий; повтор загрузки уже
записанного аудио закрытого звонка остаётся доступным в открытой карточке.
Сохранение аудио в IndexedDB после закрытия страницы здесь не добавляется.

Событие, созданное до finish, может быть получено сервером после него: сервер
сохраняет прежний 409, исходный конверт остаётся в очереди своей карточки.
Уже принятый UUID повторно подтверждается как duplicate и после finish.
Клиентская проверка не заменяет серверную и не реализует транзакционный finish v2.

Действия звонка: `call_dial {call_id, phone_ext}`, `call_answer {call_id}`,
`call_hangup {call_id}`. UI state machine: idle → dialing → ringing → talking → ended.
Удержание (HQ-033): `call_hold {call_id, report_choices?, report_modes?, voice_failures?,
report_parts?, report_loudness?, registration_number?}` / `call_resume {call_id}` — идущий
разговор встал на удержание / снят с него; звонок остаётся `talking`, `call.state` не меняется.
Поля снимка доклада у `call_hold` имеют ровно ограничения `call_hangup`; клиент отправляет
накопленный снимок вместе с удержанием, до закрытия вкладки. Сервер пишет исходный payload
без нормализации UUID. Повтор того же `client_event_id` возвращает прежний receipt; новый
hold уже удержанного звонка — `409 hold_state`, поэтому срок нельзя продлевать повтором.
Оценщик берёт последний явный снимок (пустой `report_choices: []` — доклада нет);
resume и отсутствие нового снимка не стирают предыдущий. Hold/timeout без снимка дают
`reported=0`, а не прежний fallback «соединение = доклад».
Worker ограничивает непрерывное удержание 180 секундами по серверному `server_ts`
последнего `call_hold`, даже если вкладка закрыта или карточка завершена. `call_resume`
снимает срок, следующее удержание начинает новый. По истечении срока приходит обычное
`call.state` со значением `ended`; клиент убирает локальную удержанную линию. Повторный
отбой уже завершённого звонка возвращает `409 call_ended`, не блокирующий outbox.
Отбой существующего звонка разрешён после закрытия карточки, но не после завершения
занятия; правила создания новых звонков не меняются.
В моке переключаются dialing/talking/ended; гудки, ringing и запись — T-014.
Загрузка: `POST /calls/{id}/audio`, multipart поле `audio`, WAV/WebM/Ogg ≤ 10 МиБ.
В D1 upload отвечает 501; это явно проверяемый сценарий ошибки для софтфона.
Транскрипт nullable до T-036a. `audio_url` nullable до T-008.

Состояния карточки (дополнение C-01 24.09): added → received → accepted/rejected;
rejected → accepted или redirected; accepted → responding/arrived/working/completed/refused;
далее этапы только вперёд, до completed/refused. `open` не меняет статус.
Полный автомат и причина отказа — [I-TIME v3](I-TIME.md#v3).
Контроль переходов и расчёт 30/180 секунд — T-008/T-006. Мок хранит присланный статус без оценки.

## Показ экрана ученика преподавателю (HQ-017, 18.10)

Решение Dani 18.10: видео без звука, 5 кадров/с. Управление — HTTP, кадры — отдельный WebSocket.

- `POST /sessions/{id}/screens/{user_id}/request` — преподаватель (автор идущего занятия) просит
  показ; `POST …/stop` — остановка (преподаватель или сам обучаемый); `GET /sessions/{id}/screens` —
  текущие показы. Запрос и остановка пишутся в `audit_log` (обычный аудит мутаций).
- Событие основного `/ws`: `screen.state` с payload `ScreenShare {session_id, user_id, state,
  requested_at}`, `state` ∈ `requested | sharing | paused | stopped`. Получают автор занятия и сам
  обучаемый. `paused` — сокет показа открыт, но у преподавателя сейчас нет открытого `/ws/screen`
  (закрыл вкладку «Хода занятия»): обучаемый не шлёт кадры и видит «Показ включён, преподаватель
  сейчас не смотрит». Преподаватель подключился — снова `sharing`, кадры идут.
- Кадры: `WS /ws/screen?session_id=<uuid>`, тот же cookie и проверка origin, что у `/ws`.
  - Обучаемый (только после запроса преподавателя и своего согласия — кнопка и разрешение
    браузера `getDisplayMedia`) шлёт **бинарные** сообщения — JPEG целиком (начинается с `FF D8`),
    не больше 256 КиБ; сообщение больше 320 КиБ сервер не дочитывает и рвёт сокет (1009,
    `ws_max_size` uvicorn). Сервер принимает не чаще 1 кадра в 150 мс (5 кадров/с с запасом на
    дрожание таймера); лишние, большие и не-JPEG кадры молча отбрасывает, но 20 отброшенных подряд —
    закрытие 4400. Кадры в состоянии `paused` (могли быть в пути, когда пришла пауза) не хранятся и
    не пересылаются, но проходят те же ограничения частоты, размера и формата и те же 20 подряд. Текстовое
    сообщение — закрытие 4400. Подключение без запроса — закрытие 4404; вторая вкладка того же
    ученика вытесняет первую (4409). Пока сокет открыт — `sharing` или `paused`; обрыв без «Остановить показ»
    возвращает `requested` (после перезагрузки ученик видит запрос снова).
  - Преподаватель получает **бинарные** сообщения: 16 байт UUID обучаемого + JPEG. Только
    последний кадр каждого показа; медленному получателю промежуточные кадры не досылаются.
    Сам он ничего не шлёт (текст — 4400).
  - Кадры хранятся только в памяти API (последний на показ) и удаляются при остановке; в БД,
    журналы и логи не пишутся. Завершение занятия закрывает все показы: сокет просмотра
    преподавателя — 4000, сокет показа ученика — 1000 (как «Остановить показ»: показ окончен,
    `screen.state stopped`). Сигнал — NOTIFY `session.finished`, а если он потерян — проверка
    статуса занятия (не реже раза в 5 с, пока открыт сокет показа или просмотра; показы в
    `requested` без сокетов — при следующем запросе, списке показов или подключении).
  - Чужой преподаватель, администратор, обучаемый не из занятия, не идущее занятие — 4403/4404.
- Ограничение: состояние в памяти одного процесса API — стенд запускает один процесс uvicorn.
