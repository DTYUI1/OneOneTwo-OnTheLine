# Связка «Оператор 112» → диспетчер ДДС · шаг 1 принят

Задача DT-03 (#66), реализация — DT-04
(#67). Статус: **принятый контракт шага 1** (оператор-бот), 08.10.2026. Шаг 2 (живая пара) —
по-прежнему предложение, раздел 6.

Решение тимлида 03.10: два шага. Шаг 1 — карточка 112 приходит диспетчеру из готовой записи
(«оператор-бот»). Шаг 2 — живая пара двух обучаемых, если останется время.

Пометки по CONTRIBUTING: «есть в коде» — со ссылкой на файл; «предлагаю» — того в коде нет.

## Принято 08.10

Встречи по связке не было. Предложения таблицы §2 страницы встречи 04.10
приняты как есть: тимлид не возражал, пользователь сказал делать.

1. Источник шага 1 — готовая запись оператора в `data/link112/records/` поверх сценария
   оператора. Попытка обучаемого — источник шага 2.
2. К демо один сюжет: пожар (`fire_apartment_smoke`), служба 101, ловушка
   «Дубнинская / Дубининская». Остальные сюжеты и службы — если останется время, не в DT-04.
3. Где диспетчер получает карточку: **преподаватель назначает сценарий связки в занятии**, как
   любой другой. В случайный выбор ступеней тренировки сценарии связки не попадают.
4. Ошибку оператора в адресе диспетчер **не исправляет в поле адреса** (решение 04.10 в
   `docs/decisions.md`). Уточнённый адрес — в комментарии и в разговоре с расчётом.
5. Карточка «не в ту службу» — не в DT-04 (открытый вопрос 2).
6. Ошибки оператора считаются в модуле оператора (`apps/api/app/operator/faults.py`), без
   `contract:` к evalcore.
7. Что карточка от бота, диспетчер видит только в разборе; в АРМ — нет.
8. Недочёты `card_for_dispatch` исправлены в DT-04 (раздел 2).

Принцип: диспетчер работает с карточкой такой, как её заполнил оператор; бригада живёт по
правде сюжета; диспетчер оценивается по тому, что мог знать из карточки и докладов. Ошибка
оператора на балл диспетчера не влияет.

## Термины

| термин | что это |
|---|---|
| сюжет | правда события: сценарий оператора (что, где, кто пострадал, какие службы нужны) и доклады бригад служб |
| запись оператора | карточка 112 в виде ввода оператора (`CardInput`, `apps/api/app/operator/router.py`) с привязкой к сценарию оператора |
| передача | результат обработки записи: карточка 112 по `card.schema.json`, ошибки оператора, выдача по службам |
| карточка ДДС | обычная карточка АРМ ДДС (`cards`), источник которой — карточка 112 из передачи |
| план докладов | `TrainingPlan` (`c01.schema.json`, таблица `scenario_training_plans`) — доклады бригады сценария ДДС |
| ошибка оператора | расхождение карточки 112 со сценарием оператора: адрес, тип, службы |

## 1. Запись оператора

Файл `data/link112/records/<id>.json`, формат —
[link112-record.schema.json](link112-record.schema.json), пример —
[`examples/link-112-dds-record.json`](examples/link-112-dds-record.json) (совпадает с
загружаемой записью, это проверяет тест). Телефоны в `card` — пустая строка или `+7` и
десять цифр.

Записи не правятся руками: их собирает генератор из сценария оператора, и каталог содержит
ровно то, что он собрал (`test_operator_dispatch.py`):

```sh
uv run --package arm112-api python -m app.tools.build_link112_records
```

| запись | что заложено | уровень |
|---|---|---|
| `fire_apartment_smoke.correct` | оператор записал всё верно: Дубнинская улица, дом 12, кв. 47, подъезд 2, этаж 5, ориентир, ФИО, статус и номер заявителя | 1 |
| `fire_apartment_smoke.wrong-street` | к демо: «Дубининская» вместо «Дубнинской» (бригада едет не туда) и не отмечена газификация (служба 104 карточку не получает) | 1 |
| `fire_apartment_smoke.wrong-street-level2` | та же ловушка улиц при верных службах, осложнение | 2 |

Каждая запись — свой сценарий ДДС для службы 101: преподаватель выбирает по названию
(`title`) и уровню.

| поле | что |
|---|---|
| `id` | стабильный ключ записи, `<operator_scenario_id>.<вариант>` |
| `title` | для преподавателя: что это за запись |
| `operator_scenario_id` | сценарий оператора `data/operator/scenarios/<id>.json` — правда сюжета |
| `level` | 1 — полный цикл бригады, 2 — осложнение (как в `app/seed/practice.py`) |
| `elapsed_s` | сколько оператор «говорил»; в шаге 1 не используется, нужен для оценки оператора в шаге 2 |
| `card` | ввод оператора **в форме `CardInput`**, как в теле `POST /api/operator/save` |
| `teacher_note` | какие ошибки заложены — для преподавателя |

Почему `CardInput`, а не готовая карточка: запись проходит тот же путь, что попытка оператора
(`card_for_dispatch`), а ошибки считаются той же проверкой, что оценка оператора. Из записи
построитель берёт только карточку и уровень — в шаге 2 их даст попытка.

## 2. Из записи — карточка 112

`card_for_dispatch` (`apps/api/app/operator/router.py`, есть в коде) собирает карточку по
`card.schema.json` — для сохранённой попытки и для записи одинаково.

| поле `card.schema.json` | откуда |
|---|---|
| `number` | из id передачи (у попытки — id попытки): одна карточка 112 — один номер для всех служб |
| `incident_type_code`, `incident_class` | ввод оператора; класс — имя типа из классификатора |
| `caller_name` | ввод оператора; пустое остаётся пустым — имя из сюжета в карточку не попадает |
| `caller_status` | ввод оператора (очевидец, родственник…); пустой — пусто; АРМ ДДС его показывает |
| `phone_aon` | сценарий оператора (`caller.phone`): АОН руками не вводится |
| `phone_provided`, `phone_scene` | ввод оператора по маске АРМ 112 «+7 (___) ___-__-__»: `+7XXXXXXXXXX` или пусто; неполный номер не проходит `CardInput` (422) |
| `address`, `description` | ввод оператора, с ошибками как есть; адрес полный — с объектом, строением, подъездом, этажом, кодом и описательным адресом |
| `tags`, `victims`, `blocked_people` | теги оператора; теги — подписями (`TAG_RU`) |
| `ambulance_refused` | `off_site` оператора |
| `emergency` | ввод оператора `emergency` — необязательное поле `CardInput`, по умолчанию `false` ([contracts/operator/evaluation.md](operator/evaluation.md)); на экране оператора отметки нет, её может поставить запись |
| `service_ids` | службы оператора целиком — каждая служба видит, кому ещё ушла карточка |

Без типа происшествия карточки нет; такая запись не загружается (ошибка seed).

## 3. Передача и выдача по службам

Построитель — `build_handoff` (`apps/api/app/seed/link112.py`): на входе запись, сценарий
оператора, сюжет и номера служб из справочника. Пример вывода —
[`examples/link-112-dds-handoff.json`](examples/link-112-dds-handoff.json) (сверяется тестом).
В шаге 1 передача не хранится: её роль играют файлы и стабильные UUID.

`faults[]` — ошибки оператора (`operator_faults`, `apps/api/app/operator/faults.py`), та же
проверка, что в критериях оператора «Адрес», «Тип происшествия», «Службы»:

| `kind` | поля | `effect` |
|---|---|---|
| `address` | `field`, `card`, `truth` | `wrong_place` — улица или дом (бригада по карточке приедет не туда); `imprecise` — остальное |
| `incident_type` | `card`, `truth` | `wrong_type` |
| `service_missing` | `service_id` | `not_delivered` |
| `service_extra` | `service_id` | `extra_dispatch` |

`deliveries[]` — по одной на службу карточки и на пропущенную службу:

| `status` | когда | что в системе |
|---|---|---|
| `delivered` | у сюжета есть доклады бригады этой службы | сценарий ДДС `scenario_id`; `plan` — `truth` или `wrong_address` |
| `no_plot` | служба в карточке, а докладов её бригады в сюжете пока нет | ничего (к демо доклады есть только у 101) |
| `not_delivered` | служба нужна сюжету, оператор её не выбрал | ничего |

## 4. Сюжет: доклады бригад

Файл `data/link112/plots/<operator_scenario_id>.json`: блок `services` в формате
`data/practice/*.json` (`departure`, `full`, `complication`) и для ошибки адреса —
`wrong_address.arrival`. В нём `{street}`, `{house}` и другие поля адреса подставляются из
карточки: бригада приезжает по адресу карточки, не находит происшествия, докладывает
уточнённый адрес и уже на месте по правде — этот доклад обосновывает «Прибытие». Поле
`source` — откуда взяты ход работ и формулировки.

Отдельный файл, а не поле сценария оператора: `contracts/operator/scenario.schema.json` не
меняется. К демо — сюжет `fire_apartment_smoke`, служба 101; доклады — по происшествию
тренировки `data/practice/smoke-apartment.json` того же типа и правде сценария оператора.
Голос докладов и реплик — записи банка озвучки (наборы `data/voices/bank-v*`, голос службы
бригады): берётся фраза банка той же службы с точно тем же текстом (книги службы и
`scripts/voices/bank/link112/<служба>.json` — реплики сюжетов дословно). Записи нет —
реплика уходит текстом (её диспетчер засчитывает кнопкой «Принял»). Доклад о прибытии не туда свой у каждой записи, которая уводит
бригаду: в нём адрес из её карточки, поэтому и фраза банка для него своя.

## 5. Сценарий ДДС и оценка

На каждую выдачу `delivered` — сценарий по `scenario.schema.json`, как `scenario_payload` в
`app/seed/practice.py`:

- `id` — `uuid5(NAMESPACE_URL, "arm112:link112:<id записи>:<служба>")`, повторный seed ничего не меняет;
- `card` — карточка 112 из раздела 2, `target_service_id` — служба, `level` — уровень записи;
- план — доклады сюжета первой учебной бригады службы; каждый ждёт статуса диспетчера
  (`requires_state`) и обосновывает следующий (`justifies_state`), как в тренировке;
- `complications` — `["wrong_address"]`, если ошибка адреса уводит бригаду;
- `origin` — `template`, `status` — `approved`;
- `teacher_comment` — «Связка 112 → ДДС, карточка от оператора-бота: …» + `title` и
  `teacher_note` записи. Источник карточки виден преподавателю; в АРМ диспетчеру — нет.

`evaluate` и критерии evalcore не меняются, всё выражено через `reference`:

| поле `reference` | откуда |
|---|---|
| `expected_flow` | поток уровня записи: полный цикл или осложнение, как в `app/seed/practice.py` |
| `expected_service_ids` | `[служба]` |
| `expected_address` | адрес правды, если бригада доложила уточнённый адрес (`wrong_place`); иначе адрес карточки. Поле адреса у ДДС не вводится, поэтому критерий «Адрес» ищет адрес в комментарии |
| `expected_call` | `required: false` — звонок своей службе не нужен (GP-04, `scenario-events.md`, «Звонок своей службе не обязателен»); обязательные звонки задают события |
| `expected_comment` | описание из карточки + текст последнего доклада |
| `required_fields` | `service_number`, `comment` |

Загрузка: `python -m app.seed.training` (вместе со сценариями тренировки), функция
`seed_link112`. Новых таблиц и HTTP-эндпоинтов шаг 1 не добавляет.

Тренировка: `step_pool` (`app/api/sessions/practice.py`) берёт только `practice_candidate` —
не упражнение, не параллельную смену и не сценарий связки (`is_link_scenario`).

## 6. Шаг 2: живая пара (предлагаю, не реализовано)

Отличия от шага 1:
- запись появляется в момент `POST /api/operator/save` в занятии пары, а не из `data/`;
- сценарии ДДС создаются во время занятия, а не seed'ом (в `scenario.schema.json` уже есть
  `origin: "trainee"`);
- назначение создаётся участнику-диспетчеру нужной службы сразу (`due_at = now`), дальше — тот же
  планировщик;
- оператору нужен обратный разбор по чужим карточкам — правила доступа сейчас нет
  (`GET /api/operator/attempts*` фильтрует по `actor_id`).

Уже заложено: передача — один формат для записи и попытки (`source.kind` = `record` |
`attempt`); построитель берёт из записи только карточку и уровень; номер карточки — из id
передачи.

Предлагаю таблицы шага 2: `handoffs` (id, session_id, source_kind, source_id,
operator_user_id, operator_scenario_id, card jsonb, faults jsonb, created_at) и
`handoff_deliveries` (handoff_id, service_id, status, scenario_id, assignment_id). Для jsonb
нужна JSON-схема в `contracts/` (CONTRIBUTING). Роль в паре: у `session_participants` есть
служба ДДС, но нет роли «оператор 112» — нужно поле или отдельная связь.

Позже ошибки оператора ложатся на события сценария ([scenario-events.md](scenario-events.md),
DT-10): неверный адрес — `clarify` (бригада просит уточнить адрес, диспетчер звонит заявителю
по АОН), пропущенная служба — `request_service`.

## 7. Открытые вопросы

1. Разбор у диспетчера: «карточка от оператора-бота» и ошибки оператора, которые коснулись его
   службы. В ответе разбора (`GET /api/cards/{id}/analysis`) источника карточки нет — нужно
   поле, это `contract:` PR к OpenAPI и правка `apps/web/src/arm/results/CardReview.tsx`. Пока
   источник и ошибки видит только преподаватель, в `teacher_comment` сценария.
2. Карточка пришла службе «не по профилю» (оператор добавил службу руками): правильное решение
   диспетчера — принять (бригада съездит зря), «Не принята» или перенаправить? Предлагаю
   «принять»: диспетчер не может проверить, но нужен ответ по памятке ДДС.
3. Доклады остальных служб сюжета пожара (102, 103, MOSLIFT) и три других сюжета оператора —
   если останется время.
4. Шаг 2: в паре диспетчер ждёт, пока оператор говорит (минуты). Даём ему в это время обычные
   карточки или пара работает по очереди?
5. Отметка ЧС на экране оператора: поле `emergency` в `CardInput` есть, отметки в интерфейсе
   нет. Нужна ли она — решает модуль оператора.
