## Файлы и вызов

- [c01.schema.json](c01.schema.json): `TimingPolicy`, `ClockSample`, `TimingEvent`,
  `TimingInput`, `TimingResult`, `TimingEvidence`, `WaitingInterval`, `TimingFixture`.
- [timing-v2.json](examples/timing-v2.json): единый массив 24 числовых примеров Python/TS.
- Python: `evalcore.timing_contract`, `TimingCalculator.__call__(TimingInput) -> TimingResult`.
  V-01 реализует `evalcore/timing.py:calculate_timing` с этой сигнатурой.
- TS: `shared/contracts.ts`, `TimingCalculator = (input: TimingInput) => TimingResult`.
  C-02 реализует `shared/timing.ts:calculateTiming`; Dwots/Brikkerdev используют её.
- `dataclasses.asdict` сохраняет JSON-форму. На HTTP-границе валидирует JSON Schema;
  dataclass сама не является валидатором внешнего ввода.

Все поля новых объектов обязательны, кроме явно необязательных HTTP-расширений.
`null` — неизвестно/не применимо, `0` — известное нулевое значение.
Времена — ISO UTC с `Z`; длительности в секундах, поправка/RTT — в миллисекундах.
Числа конечны; negative duration, boolean вместо числа и неизвестные поля недопустимы.

Адаптер C-02 отображает StoredEvent.id в TimingEvent.event_id, `status_change` в kind=status,
deliver/open/redirect — в одноимённый kind; state берёт из status_change.payload.state,
для остальных kind state=null. Прочие действия не входят во временной вход. clock —
разрешённый по clock_sample_id образец, а не число из legacy clock_offset_ms.

## Снимок и интервалы

`TimingInput.snapshot_id` — UUID занятия. `policy` — его неизменяемый снимок v2;
`policy=null` обозначает legacy v1. Отсутствие сохранённой версии C-02 отображает в `null`,
не объявляет историю v2. Два `legacy_*_normative_s` берутся из старого снимка занятия,
используются только при `policy=null`. Глобальные текущие `/settings` не участвуют.

Для новых занятий `POST /sessions` получает необязательный `timing_policy`.
Нормативы политики должны совпадать с `settings_snapshot`; противоречие → 422 в C-02.
**C-02, 24.09:** в database-режиме `timing_policy` сохраняется в снимке занятия
(`sessions.timing_policy`, миграция 0007) и читается через `/sessions/{id}/lifecycle`.
Без поля новое занятие получает v3 (`TimingPolicy.examples[1]`) с нормативами
`settings_snapshot`; явный `null` — legacy v1; старые занятия остаются `null`.
Mock-режим и новые clocks (`clock_sample_id`, `/clock/samples`, WS v2) по-прежнему 501.
Точные дефолты политики находятся в `TimingPolicy.examples[0]`: версия 2, 30/180,
`waiting_policy=separate`, RTT ≤2000 мс, возраст измерения ≤60000 мс, буфер ≤30000 мс,
допуск будущего времени ≤250 мс. C-02 записывает эти значения в snapshot, а не читает
глобальные константы при каждой оценке. Изменение методики требует новой версии.

Прогноз нового занятия получает тот же snapshot через `PredictionContext`
(contract_version=2, snapshot_id, policy) и Protocol `SessionPredictor`.
`policy.handling_normative_s` — порог превышения, отдельно от параметров Trainee.
CalibrationObservation хранит норматив завершённой попытки и качество её времени;
при неизвестных исторических данных передаётся null без подстановки текущих настроек.
Отображение C-06 и правила legacy — [контракт прогноза](evalcore.md).
Эта форма пока не подключает V-03/C-06 к действующему scheduler.

1. Порядок входных событий — подтверждённый порядок действий/реплея, а не сортировка
   по часам клиента. Дубликаты `(actor_id, client_event_id)` устранены API.
2. Реакция: первое подтверждённое `deliver` → первое `open`. Первым вручением считается
   рендер строки, подтверждённый действием; `appeared_at` не заменяет deliver.
3. Обработка: первое `open` → первое `status` с `completed/refused` или `redirect`.
   `rejected` не терминал v2. Повторные `open` не меняют начало.
4. `lifetime_s`: `appeared_at` → terminal. При отсутствии terminal — `null`;
   текущее время для live-счётчика берётся из `observed_at`, не записывается как итог.
5. `waiting_s`: длина объединения подтверждённых интервалов ожидания в границах
   open→terminal (или open→observed_at для активной попытки). Пересечения не суммируются
   дважды. `ended_at=null` ограничивается `observed_at`. Нет open → `0` при известном
   пустом ожидании, иначе `null`. `waiting=null` означает отсутствие журнала, `[]` —
   подтверждённое отсутствие ожидания. Недостоверные границы дают `null` и anomaly.
6. `active_handling_s=handling_s-waiting_s`, только если обе величины известны.
   Учебная обработка остаётся полным open→terminal; ожидание показывается отдельно.
   C-06 не назначает штраф за ожидание недоступных сведений: соответствующий слой
   остаётся partial до достаточного evidence. C-01 не вводит новую формулу балла.
7. Равенство нормативу допустимо. `*_overdue = duration > normative` только при
   достоверном измерении. Missing или качество estimated/invalid → `null`, не false.
8. Отрицательный интервал → `null`, `quality=invalid`, `non_monotonic`;
   не брать абсолютное значение и не прижимать к нулю. Остальные независимые
   интервалы сохраняются, но overdue при invalid не используется для штрафа.

## Проверяемая синхронизация

Текущий сервер сохраняет `server_received-client_sent`: это одностороннее измерение,
включающее сетевую задержку. Оно **не** подтверждает midpoint. Текущий frontend
рассчитывает midpoint для показа, но это также не сохранённое проверенное измерение API.
Исторический `clock_offset_ms=0` не доказывает синхронизацию.

Стык C-02: клиент отправляет `clock.ping.v2 {sample_id, client_ts}`; сервер сохраняет
sample_id/actor/время получения и отвечает `clock.pong.v2` с тем же ID/client_ts и
собственным `server_ts`. Клиент получает ответ в `client_received_at` и подтверждает
`POST /clock/samples` телом `ClockSample`. Повтор ID с теми же данными — прежний receipt,
с другим телом/actor — 409/404. Событие ссылается необязательным `clock_sample_id`.
Сервер проверяет принадлежность и совпадение с сохранённым pong; чужая поправка запрещена.
**C-02, 25.09:** в database реализовано — таблица `clock_samples` (миграция 0008), pong v2 несёт сохранённый server_ts (мс), `POST /clock/samples` проверяет владельца, совпадение с pong и формулу; `CardEvent.clock_sample_id` принимает только подтверждённый образец (иначе 422 `clock_sample_unknown`). Клиент `shared/ws` шлёт v2 на каждом heartbeat и прикладывает свежий образец (≤55 с) к событиям; при закрытии 4400 (mock) остаётся на v1. В mock HTTP 501 и WS v2 → 4400, как раньше.

`offset_ms = server_at - (client_sent_at + client_received_at)/2`;
знак **server − client**. Нормализованное время действия = `client_ts + offset_ms`.
RTT = received−sent. Ошибка соответствия формуле более 1 мс, отрицательный RTT,
RTT выше policy.max_rtt_ms или отсутствие received/offset → `invalid_sample`.
`legacy_one_way` всегда `legacy_clock`; отсутствующая запись → `missing_clock`.
Возраст = event.client_ts−sample.client_received_at; вне [0,max_sample_age_ms] → stale.
Поправка проверяется у каждого события; смена часов между ними не маскируется.

Если normalized > server_ts+future_tolerance_ms → `future_event`;
если server_ts−normalized > max_buffer_delay_ms → `buffer_exceeded`.
В этих случаях используется **server_ts**, `source=server_fallback`, причина в evidence,
`quality=estimated`, `untrusted_clock`. Время пригодно для показа как оценочное,
но не для автоматического штрафа. В пределах future tolerance время не прижимается:
последующая проверка хронологии всё равно обязательна.
Доставка накопленной очереди через ровно 30 с с проверенной поправкой сохраняет
исходные 20/170. Сырые client_ts/server_ts/образец остаются без изменений.

Качество: invalid имеет приоритет над estimated, затем verified; legacy — отдельный режим.
Missing boundary добавляет `missing_deliver/open/terminal`, соответствующая длительность
null. Evidence содержит одну запись на входное событие в том же порядке; русское
пояснение UI формирует по стабильным reason/anomaly, не выдаёт машинный enum пользователю.

## Legacy и проверка

Вход `policy=null` в адаптере v1 сохраняет прежние client_ts и терминальность `rejected`.
Это не единый новый норматив для всех старых экранов: старые сохранённые отчёты/оценки
остаются как есть. C-02 не переписывает card_events/evaluations/predictions.
Фикстура `legacy_rejected_boundary` даёт обработку 20, соответствующая v2 — 170.

Примеры покрывают: 0/20/40/190→20/170; нулевой интервал; 30/180 и превышение на 1 мс;
повтор open; отсутствие каждой границы; refused; rejected→redirect и незавершённый
rejected; два снимка; положительную/отрицательную/нулевую поправку; буфер 30 с;
missing/одностороннее измерение/неверную поправку/устаревание/будущее/длинный буфер;
нарушение порядка; известное и неизвестное ожидание; legacy.
Тесты C-01 проверяют форматы, типы и смысл чисел, **не заявляют реализацию V-01/C-02**.

## Версия 3 · дополнение C-01 от 24.09.2026

**25.09:** `evalcore/timing.py:calculate_timing` (v1/v2/v3) и `apps/web/src/shared/timing.ts`
проходят все 42 примера; сервер отдаёт результат в `AttemptAnalysis.timing`. Python-версия —
перенос капитана для C-06; V-01 может заменить её при тех же примерах.

Статус: **contract-ready**. Расчёт `calculate_timing` для v3 — V-01 (Verwelius),
адаптер событий, snapshot и общий TS-модуль — C-02 (капитан). Эта поставка задаёт форму,
смысл и 18 числовых примеров [timing-v3.json](examples/timing-v3.json); реализацию
расчёта она не заявляет. Схемы v2 расширены совместимо: прежние входы и примеры валидны.

**Политика.** `TimingPolicy.timing_version=3` требует `waiting_policy=exclude_confirmed`,
v2 — `separate`; другое сочетание отклоняется схемой. Нормативы, RTT, возраст измерения,
буфер и допуск будущего времени — как в v2 (`TimingPolicy.examples[1]`). Новые занятия
получают v3 после подключения C-02; занятия и попытки со снимком v2/legacy пересчитываются
по своей версии. Калькулятор выбирает правила по `policy.timing_version`, `null` — legacy v1.

**Направление.** Новый вид события `kind=direct` — фактическое направление карточки
конкретному обучаемому: строка появилась на его АРМ. С 27.09 C-02 строит его из первого
`deliver` карточки, нормализованного тем же расчётом и по тем же правилам часов, что прочие
действия обучаемого (без подтверждённого образца — серверное время deliver, `cards.delivered_at`);
`event_id` — ID карточки, `client_ts=server_ts`, `clock=null`. Нет deliver — нет и `direct`
(`missing_direct`): карточку, которую обучаемый не увидел, реакцией не судим. Время выдачи
scheduler'ом (`cards.appeared_at`), планирования и восстановление snapshot направлением не
являются; `appeared_at` остаётся началом `lifetime_s`. Прерванная попытка (`interrupted_at`)
считается до момента прерывания. (До 27.09 направлением было `cards.appeared_at`.)
Evidence такого события: `source=server`, `reason=server_event`; качество оно не понижает.

**Правила v3.** Порядок событий, нормализация часов, anomalies часов и `invalid`/`estimated`
для отдельных событий — как в v2, пункты 1 и 8 и раздел синхронизации ниже.

1. Реакция `reaction_s`: первое `direct` → первое `status` с `accepted` или `rejected`.
   `open` и `deliver` реакцию не закрывают. Нет `direct` → `null` и `missing_direct`;
   нет первичного статуса → `null` и `missing_primary_status`. Возврат
   «Не принята → Принята» реакцию не меняет: считается первый первичный статус.
2. Полная обработка `handling_s`: первое `open` → terminal. Terminal v3 — первое из
   `status` `completed`/`refused` или `redirect`; если его нет, а последний первичный статус —
   `rejected` без последующего `accepted`, terminal — этот `rejected`. Этапы `responding`,
   `arrived`, `working` terminal не являются. Повторный `open` начало не сдвигает.
3. `lifetime_s`: `appeared_at` → terminal, как в v2.
4. `waiting_s`: объединение подтверждённых интервалов ожидания в границах open→terminal
   (open→`observed_at` для незавершённой попытки), как в v2 п.5. Обычное бездействие
   и работа с другой карточкой ожиданием не считаются: интервал создаёт только журнал
   ожидания учебного сообщения (C-02/C-04).
   **27.09, бригада звонит сама.** Интервал доклада — пока бригада работает: от отправки
   (первый отвеченный звонок этой бригаде) или от статуса `requires_state`, что позже, до
   готовности доклада (`+ available_after_s`). Промедление диспетчера с ответом на её
   входящий звонок — активное время, не ожидание. Выдачи до миграции 0012 считаются
   по-старому: от ответа на звонок до выдачи реплики.
5. `active_handling_s = handling_s − waiting_s`, только если обе величины известны.
6. `reaction_overdue = reaction_s > reaction_normative_s`;
   **`handling_overdue = active_handling_s > handling_normative_s`** — в этом отличие от v2.
   Неизвестное ожидание (`waiting=null`) даёт `active_handling_s=null`,
   `handling_overdue=null` и `waiting_unavailable`, а не сравнение полной длительности.
   Равенство нормативу допустимо; missing/`estimated`/`invalid` → `null`, как в v2 п.7.
7. Длительности — точные разности миллисекундных меток (0,001 с), без округления вверх.
   `anomalies` перечисляются в порядке enum схемы.

Пример поправки: направление 0, open 20, «Принята» 40, «Работы завершены» 190 →
реакция **40**, полная **170**, активная **170**; при подтверждённом ожидании 60 с
активная **110**, полная остаётся 170. Тот же вход в v2 даёт 20/170.
Примеры v3 покрывают: базовый и с ожиданием; неизвестное ожидание; open до 30 с при
статусе после 30 с; игнорирование `deliver`; повтор open; точные пороги и превышение
на 1 мс; ожидание, удерживающее активную обработку в нормативе; объединение и обрезку
интервалов; все этапы; «Не принята → Принята»; окончательную «Не принята»;
перенаправление; отказ от работ; отсутствие направления; живую попытку без статуса
и с открытым ожиданием.

**Статусы карточки v3.** Добавлены `arrived` («Прибытие») и `working`
(«Проведение работ»), [памятка ДДС](../docs/dataset/README.md), стр. 22–25. Автомат
универсален для служб и хранится в `evalcore.defaults.CARD_TRANSITIONS`:
received → accepted/rejected; rejected → accepted (и отдельное действие redirect);
accepted → responding/arrived/working/completed/refused; responding → arrived/working/
completed/refused; arrived → working/completed/refused; working → completed/refused.
Этапы идут только вперёд, пропуск допустим: обязательные этапы задаёт эталон сценария.
`rejected`, `refused` и `redirect` с пустым после trim комментарием → 422 `reason_required`.
`completed`/`refused`/`redirected` закрывают карточку для правок, как раньше.
Автомат — надмножество прежнего: сохранённые попытки остаются допустимыми и
не переинтерпретируются. Отображение этапов в АРМ/live/replay — D-03/B-03.
