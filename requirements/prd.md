## 2. Цель продукта (одним абзацем)

Локальный веб-тренажёр, который **воспроизводит АРМ ДДС системы-112**, по команде преподавателя
(или ИИ) **раздаёт обучаемым карточки происшествий**, фиксирует их действия, **автоматически
оценивает** (время, полнота, ошибки ввода, маршрутизация по службам, доклад по телефону),
**объясняет** вердикт, даёт преподавателю переопределить его и формирует **отчёты**; сложность
заданий **адаптируется** к уровню обучаемого. Заказчик оценивает «общее ощущение, что это
действительно помощник преподавателя», а не сложность модели. [Q&A Q7, Q24]

## 4. Пользователи и роли

### 4.1 Администратор [ТЗ §8]
Управляет техническим состоянием: запуск/остановка сервисов, мониторинг, обновление, бэкап
(≥1 раз в сутки), учётные записи всех ролей, RBAC, настройки телефонии/БД/логов/безопасности,
системные журналы и аудит. **Не может** вмешиваться в учебный процесс (менять оценки/сценарии во
время занятия), удалять критичные данные без бэкапа.

### 4.2 Преподаватель (главная роль) [ТЗ §8, Q&A Q3, Q22]
- Создаёт/редактирует/**утверждает** сценарии, в т.ч. сгенерированные ИИ; классифицирует по сложности.
- Назначает задания конкретным рабочим местам / группам (одновременно разные уровни разным местам).
- Видит выполнение в реальном времени (~10 обучаемых в поле зрения, до 23 в классе).
- Видит результаты: автооценка ИИ + своя экспертная оценка; **приоритет преподавателя над ИИ всегда**;
  переопределения фиксируются в журнале и используются для дообучения/калибровки.
- Получает отчёты и «инсайты» по типичным ошибкам группы; даёт обратную связь через систему.
- Настраивает параметры сценариев (тип происшествия, локация, сложность), **тайминг (по умолчанию 30 с)**,
  критерии успешности (пороги ошибок, требования к синтаксису).
- **Не может** менять системные настройки, удалять системные данные, вмешиваться в работу других
  преподавателей, менять оценки без записи в аудит.

### 4.3 Обучаемый [ТЗ §8]
- Видит только назначенные задания и **только профильные события своей ДДС** (ролевая модель по службам). [ТЗ §10]
- Работает в эмуляторе АРМ-112: принимает карточки из строки состояния, заполняет поля, ставит
  статусы, вводит текст свободной формой, звонит должностным лицам.
- Видит свои результаты, время реакции, историю ошибок, рекомендации; таймер в интерфейсе.
- Может сохранять промежуточные результаты (при необходимости); аутентификация при каждом входе;
  результаты хранятся в локальном профиле. [ТЗ §8]
- **Не может** видеть чужие результаты, менять сценарии/материалы, удалять результаты.

## 5. Предметная область

### 5.1 Реальный процесс as-is [Q&A §2, СКРИН]
1. Заявитель звонит в 112 → оператор 112 заполняет карточку: адрес, телефон, описание со слов
   заявителя, тип происшествия через **теги-подсказки** («Что случилось» → сценарий → теги).
2. По тегам **автоматически подтягивается список служб** (можно добавить вручную). Оператор
   нажимает «Сохранить» → карточка уходит в выбранные ДДС.
3. В АРМ ДДС в **списке происшествий (строка состояния)** появляется новая строка.
   Диспетчер открывает карточку и в течение **30 с после её направления в службу**
   ставит первичный статус «Принята/Не принята». Одно открытие подтверждает только
   технический статус «Получена службой». [ДАТА-24, стр. 21]
4. Диспетчер ставит статус **Принята / Не принята** (выбор из двух), пишет комментарий
   (свободный текст, напр. «Отправлн сантехник для перекрытия воды»), далее через «карандаш»
   ставит статусы хода реагирования, включая **Прибытие** и **Проведение работ**,
   с комментариями (§5.3). [ДАТА-24, стр. 22–26]
5. Каждый статус — с датой-временем, номером оператора и текстом; история видна во всплывающей ленте.

Дополнение: ДДС вручную выбирает необходимые бригады; используется IP-телефон ДДС,
у бригады обычно служебный мобильный. Точное место выбора бригады в реальном ПО не описано.
Общий алгоритм для всех служб разрешён прямо. Ответ 21.09, п.1.2–1.3 и 3.

Сведения об этапах по телефону — вероятная трактовка переписки, но направление звонка,
источник каждого сообщения и лицо, принимающее решение о выезде, пока не установлены.
Не приписывать изолированному ответу «Нет, только оператор ДДС» отсутствующий вопрос.
Границы достоверности.

### 5.2 Карточка происшествия — «формат 112» [СКРИН, Q&A Q12]
Ниже — инвентарь полей из двух ролей реального ПО. Рабочий экран обучаемого сверяется с
[АРМ ДДС](../docs/СКРИНШОТ%20ДДСГСИ.docx); снимки оператора 112 помогают понять источник карточки.
[Q12](../docs/C08_meeting_2026-09-16_QA.md#q12) подтверждает аутентичность полей, но не задаёт
точное разделение прав на редактирование. Текущее source/current — решение команды;
[таблица UI](../contracts/ui_spec_arm.md) помечает это допущение. Кнопки создания опросной
карты и добавления служб у оператора 112 не переносятся автоматически в АРМ ДДС.

Карточка и реестр — обязательные ориентиры визуальной приёмки: цвета, конфигурация, поля.
Небольшие отличия новых/второстепенных окон прямо допущены 21.09 12:06–12:07.
Это не числовое требование pixel-perfect. Размещение учебного выбора бригады при телефоне —
решение команды; из ответа не следует наличие такой кнопки в реальном АРМ.

- Шапка: **номер происшествия** (8 цифр, напр. 36814845), дата/время сохранения, оператор, № АРМ, логин.
- Телефоны: **АОН**, **предоставленный**, **телефон на место** (+7 маска); кнопки «записи звонков», «список SMS».
- **ФИО заявителя**, статус заявителя.
- **Адрес**: страна, субъект, населённый пункт, объект, округ, район, улица, дом/вл, корпус,
  стр/соор, квартира/офис, подъезд, этаж, код, описательный адрес; кнопка «очистить адрес».
- **Описание со слов заявителя** (до 1999 символов).
- Флаги: **Пострадавшие / Нет на месте–Отказ от скорой / Нет доступа–Заблокированные**; **нет контакта / срыв звонка**; маркеры **ЧС / ЧП**.
- **Тип происшествия** (блок «Происшествие 101» и т.п.): группы тегов «Где» (Улица / Транспорт /
  Дом / Здание-объект / Опасный объект), признак, доступ, тип дома, этажность, угроза людям,
  внутридомовые объекты, перекрытие движения, газификация, описание. Итог — строка тегов +
  **Класс** (напр. «пожар: квартира») + [ВИС] Класс.
- **Службы** (нижняя панель): Служба 101, 104, 102, 103, Деп. ЖКХ, ЦЭМП, ЦОДД, Мос.Без., Мослифт,
  ОАТИ, поселения/управы… — у каждой свой статус и время («11:14 Добавлена», «11:29 Начало реаги…»).
- **Таймер** заполнения в правом верхнем углу (мм:сс); **красное поле = время набора карточки превышено**.
- Список происшествий: колонки Связи, ЧС, Опер., АРМ, Номер, Дата, Время, Тип происшествия,
  Постр., Адрес, Статус службы + строка «Описание».
- Цветовая схема: тёмно-серый фон списка (#7d8a90-подобный), светлая карточка, оранжевая нижняя
  панель служб у оператора 112, синие активные теги. Точные цвета — снять со скриншотов.

### 5.3 Жизненный цикл карточки на стороне ДДС [ДАТА-24, КАП-24]

[Памятка ДДС, стр. 21–26](../docs/dataset/README.md) определяет технические статусы
«Добавлена» и «Получена службой», первичные «Принята / Не принята» и последующие
«Начало реагирования / Прибытие / Проведение работ / Работы завершены /
Отказ от выполнения работ». Начало реагирования означает выезд; этапы фиксируются
после получения соответствующей информации.

После «Не принята» можно выбрать «Принята». Для отказных статусов нужен комментарий
с причиной и сведениями о передаче информации при её наличии. Уточнённый адрес
и результаты работ отражаются в комментариях. Перед завершающим статусом вносятся
необходимые сведения: его сохранение закрывает карточку для редактирования.
Ошибочное завершение разрешается обращением в отдел контроля. [Памятка, стр. 22, 26, 32]

**Учебная схема команды:** принять → вручную выбрать бригаду → сообщить сведения
через симулятор телефона → получить учебные сообщения о ходе работ → отразить
этапы и результаты → завершить. [КАП-24] подтверждает универсальный алгоритм
для служб; отдельная специализация исключений 103/104 из памятки для MVP не требуется.
Разрешённые ветви и пропуски этапов задаются учебным сценарием. Дополнительный пример
обмена от заказчика не ожидается.

**Время:** 30 секунд — от направления карточки в службу до «Принята/Не принята»;
открытие карточки само по себе этот норматив не закрывает. Границы учебных 3 минут,
учёт ожидания и формулу оценки определяет команда, фиксируя версию методики и
настройки занятия. [КАП-24, FR-4.8]

Рабочая методика команды для следующей версии: 180 секунд активной обработки
от первого открытия до завершения по сценарию, исключая явно зафиксированное
ожидание недоступных учебных сведений. Полное время и ожидание учитываются отдельно.
Правила, совместимость и числовые примеры — в поправке командного плана.
Это проектное решение команды, требующее реализации общего контракта.

Старый автомат D1 и `contracts/I-TIME.md` требуют согласованного обновления:
в них есть упрощённая цепочка и расчёт реакции до открытия карточки.
Уточнение требований не означает, что эти изменения уже реализованы.

## 8. Критерии оценки (как будут смотреть)

### 8.1 Чек-лист кейсодержателя [Q&A §5]
1. Интерфейс АРМ ДДС визуально повторяет реальный.
2. Карточка «формата 112» открывается из строки состояния, заполняется; принять/отказаться/перенаправить.
3. Сценарии генерируются (шаблоны + ИИ) и **похожи на настоящие**.
4. ИИ верно отличает правильное от неправильного; вердикты объяснимы; преподаватель переопределяет.
5. Оценка по времени (30 с / 3 мин), полноте, ошибкам ввода (адреса!), маршрутизации; веса настраиваемые.
6. Полный жизненный цикл карточки; параллельные карточки.
7. Симулятор IP-телефонии: исходящий звонок, TTS разными голосами.
8. Три роли; пульт преподавателя; отчёты с графиками; лидеры/отстающие и причины.
9. 4 уровня сложности + вес 1–10; адаптивность.
10. Полностью локально; держит 10 одновременных на демо, 23 в классе.
11. Несколько ДДС, масштабируемость.
12. Простота поддержки — «помощник преподавателя».
13. Пакет по ТЗ + видео ≤ 5 мин + (опц.) публичная демка.

Эксперты будут проверять **скорее на произвольных сценариях**, но и на эталонных билетах. [Q&A Q20]
Оригинальность и глубина реализации — равнозначны. [Q&A Q24]

### 8.2 Критерии экспертизы ЛЦТ [ТЗ §16–17]
Предварительная: идея/оригинальность/способ/технологии; качество кода, интегрируемость, скорость;
проверка расчётов и **прогнозирования (достоверность)**; полнота документации.
Финальная: + сравнение прогнозов с реальными значениями, реальность рекомендаций, настраиваемые
параметры, **объективность диаграмм**, UX/UI (логически связанные блоки рядом), выступление на питче.

> «Прогнозирование» в терминах заказчика = адаптивный подбор следующего задания по истории
> результатов + предсказание, уложится ли обучаемый в норматив. [Q&A Q16]

## 10. Технические ориентиры (не требования — решения команды по Q&A)

- Всё в одном `docker-compose`, локальные CPU-friendly модели; режим «облачная модель» выключен по умолчанию.
- Оценщик = детерминированные правила (время, поля, службы по классификатору, справочник улиц)
  + лёгкая ИИ-оценка свободного текста → балл с весами и объяснением.
- Движок сценариев: шаблоны по типам из классификатора × параметры × вес; ИИ-генерация для
  высоких уровней; предгенерация пакета до занятия.
- Архитектура вокруг преподавателя: пульт, лента вердиктов с «подтвердить/отклонить», отчёты.
- Софтфон в браузере + TTS (2–3 реплики, несколько голосов); STT доклада — как «изюминка».
- Приоритетные ДДС для MVP выбрать самим (напр. 101/МЧС, 102/полиция, 103/скорая, 104/Мосгаз,
  ЖКХ/Мосводоканал, Мослифт) — с конфигурируемым добавлением остальных из классификатора.
