### BlusteryS/Training112 — https://github.com/BlusteryS/Training112
- **Команда:** не указана (в README, PDF и коде названия нет) · **создан / последний коммит:** 12.09 / 29.09 ·
  **коммитов:** 165 · **стек:** Java 21 + Vert.x, PostgreSQL (Flyway, 22 миграции), React/TS (Vite, CSS-модули),
  Python + ONNX Runtime (речь), Docker Compose; живой стенд online.tindapp.com
- **Скоуп:** оба (оператор 112 со звонком и карточкой; ДДС с готовой карточкой) · **зрелость:** полноценное решение
- **Суть:** голосовой диалог с заявителем без LLM в рантайме: Silero VAD → T-one (ASR) → дообученный
  Multilingual E5 Small INT8 классифицирует вопросы оператора в интенты сценария → заранее синтезированные
  Piper-реплики. ДДС-часть: статусная машина, где каждый следующий статус «открывает» доклад бригады по IP-телефону.
- **Интересное для нас:**
  - **LLM только на этапе подготовки сценария, не в разговоре.** Преподаватель задаёт тип ЕКП + место +
    пострадавшие + сложность → `ScenarioDraft` собирает факты; опциональная Qwen3-4B Q8 (llama.cpp, отдельный
    `compose.gpu.yaml`) лишь размножает формулировки ответов строго по факту (жёсткий system prompt + JSON-схема),
    worker озвучивает их Piper, после чего сценарий «Готов к утверждению» → преподаватель утверждает.
    В рантайме — только CPU-классификатор. Хороший ответ на «без GPU» и на галлюцинации.
    `speech/src/speech112/preparation/reply_generator.py`, `backend/.../training/ScenarioDraft.java`,
    `speech/src/speech112/contracts/draft-profile.json`.
  - **Мульти-интент в одной реплике:** «Адрес и есть ли пострадавшие?» → ответ склеивается из нескольких
    фрагментов (`compact_variants`), «повтори» отдаёт прошлый ответ, на непонятное — `clarification`,
    варианты фраз не повторяются подряд. `speech/src/speech112/runtime/dialogue.py`.
  - **Статусы ДДС, привязанные к докладам по телефону** (ровно наш скоуп): Получена → Принята/Не принята →
    Начало реагирования → Прибытие → Проведение работ → Работы завершены / Отказ от выполнения работ. Бригада
    звонит с докладом, и статус ставится только после доклада; руководитель согласует выезд или отказывает;
    бригада может сообщить «адрес в карточке не совпадает — передайте в 112» → обучаемый звонит оператору 112;
    можно перезвонить заявителю (темы address/situation/victims). Реплики — фиксированный набор WAV.
    `backend/.../training/DdsPhone.java`, `backend/src/main/resources/dds-phone.json`, `site/src/components/dds/statuses.ts`.
  - **Оценка ДДС — взвешенный чек-лист на 100 баллов** с нашими нормативами: первичный статус по полномочиям
    службы (25/50), открыта ≤30 с (15/20), первый статус ≤3 мин (10/30), бригада/отказ руководителя, каждый этап
    после доклада, итог с комментарием; провал пункта → рекомендация «Повторите: …».
    Веса меняются, если верный ответ — «Не принимать». `backend/.../training/DdsEvaluation.java`.
  - **Оценка карточки 112 с доказательствами:** рубрика сценария из типов `action` / `deadline` /
    `field_equals` / `semantic`; каждый пункт хранит `event_ids` событий, на которых основан вердикт; semantic
    без уверенности → `review` (ждёт преподавателя), зачёт = балл ≥ pass_score И ошибок ≤ max_errors И нет
    проваленных mandatory. `speech/src/speech112/preparation/evaluation.py`, `contracts/evaluation-advice.json`.
  - **Классификатор ЕКП v046 из xlsx (1139 записей) с маршрутизацией служб:** у каждого типа — службы,
    флаги `police_without_signs`, `medical_without_victims`, `victim_services`, районные/окружные ДДС, ТиНАО.
    Готовая таблица «тип → кого оповещать». `tools/import_classifier.py`,
    `backend/src/main/resources/contracts/incident-classifier.json`.
  - **Телефонная атмосфера из настоящих записей:** к голосу заявителя подмешивается шум линии и редкие
    помехи мобильной связи из реальных записей (с атрибуцией), со случайными окнами и fade. `speech/src/speech112/telephone_noise.py`.
  - **Офлайн-гео:** ФИАС Москвы и OSM-адреса в `.tsv.gz` для подсказок адреса, карта Москвы в одном
    `moscow.pmtiles` (MapLibre без тайл-сервера), клик по карте → обратное геокодирование по локальной базе.
    `site/public/maps/`, `backend/src/main/resources/contracts/`.
  - **«Подборка карточек»:** занятие ДДС из ≥2 карточек (в том числе сохранённых другими обучаемыми-операторами
    112), выдаются по одной в случайном порядке, так что связка 112 → ДДС работает между учениками. `DdsCardPool.java`, `CardLinks.java`.
  - Сдача: `deploy/setup.py` поднимает свой CA и TLS для микрофона по IP в LAN (HTTPS обязателен для getUserMedia),
    автобэкап БД в отдельном контейнере, вход по «логин + пароль + номер АРМ», видеообзор 16 МБ в репо, PDF на 5 стр.
- **Слабые места / чего нет:** реплики ДДС-телефона фиксированные, ASR-текст обучаемого ни на что не влияет
  (кроме того, что он непустой); нет live-мониторинга и вмешательства преподавателя в ходе попытки (только результаты
  и экспертная оценка постфактум); README обещает «офлайн», но модели скачиваются при сборке.
- **Куда смотреть следующему агенту:** `backend/src/main/java/com/training112/training/` (DdsEvaluation, DdsPhone,
  ScenarioDraft), `speech/src/speech112/runtime/dialogue.py`, `speech/training/` (обучение интент-классификатора на
  ru_paraphraser/CEDR/Golos).

### Dema-koder/lct2026-arm112 — https://github.com/Dema-koder/lct2026-arm112
- **Команда:** не указана (README, PDF на 29 стр.; презентация в Google Slides по ссылке из README) ·
  **создан / последний коммит:** 17.09 / 29.09 · **коммитов:** 150 · **стек:** Java 21 + Spring Boot 4.1, Spring Security
  (JWT + refresh), raw WebSocket по одноразовому ticket, PostgreSQL 17 + Flyway, React 19 + Next.js/vinext,
  OpenAPI-контракт 0.3, LanguageTool локально, llama.cpp-сайдкар (Qwen2.5-7B Q4) опционально, k6, Prometheus
- **Скоуп:** оба (режим CARD_FILL = оператор 112, CARD_ACTIONS = диспетчер ДДС) · **зрелость:** полноценное решение,
  голоса нет (звонки — события в UI, без TTS/STT)
- **Суть:** «ИИ-оценка» — детерминированные правила с весами, кодами ошибок и рекомендациями; LLM только пишет
  вводные и одно предложение-пояснение к готовому факту ошибки. Очень плотная методическая и аналитическая
  обвязка: калибровка оценки по баллам преподавателя, модель Раша, симулятор когорты, нагрузочные прогоны.
- **Интересное для нас:**
  - **Оценка ДДС с готовыми весами и штрафами, близкая к нашей:** время 30 / действия 40 / коммуникация 15 /
    грамотность 15. Просрочка принятия −40 (отсчёт от появления в журнале, открытие не сбрасывает), просрочка 3 мин
    −30, оба флага «липкие»; отказ от профильной −70, принятие чужой −40, отказ исправлен на «Принята» −10,
    «Отказ от работ» без «Прибытия» −20, комментарий короче 15 символов −30.
    `docs/assessment/ASSESSMENT_AND_SCENARIOS.md` §4, `src/main/java/ru/lct/arm112/service/assessment/CardActionsAssessor.java`.
  - **Детектор «прокликивания» CLICK_THROUGH:** статусы проставлены подряд быстрее порога `minReactionSeconds`
    → −25 и замечание «карточку не читали». Дёшево, и закрывает дыру, которую чистые нормативы открывают.
    `CardActionsAssessor.java` (~стр. 99).
  - **Ожидаемое решение выводится из службы обучаемого:** `ACCEPT`, если его служба есть в эталонных службах
    сценария, иначе `DECLINE` — один и тот же билет для 101 профильный, для 102 «не в компетенции».
    Так каждый сценарий бесплатно даёт кейсы «Не принята». `TrainingEngine.cardFrom`, там же §4.3.
  - **Интенсивность потока как рычаг сложности:** SEQUENTIAL / LOW 90–180 с / MEDIUM 45–90 с / HIGH 15–40 с
    плюс 0/3/6/10 фоновых чужих карточек в журнале; карточки копятся, и просрочки становятся главным
    механизмом сложности. Для 112: вызов звонит 30 с, пропуск → перезвон через 20 с, второй пропуск → «потерян». §5.
  - **Калибровка ИИ по преподавателю («Коррекция ИИ»):** при ≥30 явных оценках преподавателя по критерию —
    линейная поправка, проверка на отложенной выборке, админ видит ошибку до и после и включает версию вручную;
    исходный балл ИИ хранится, завершённые результаты не пересчитываются. Плюс «явное подтверждение оценки ИИ»
    как отдельное действие преподавателя. README, `docs/PROJECT_DOCUMENTATION.md` §6.5, миграция `V21__assessment_calibration.sql`.
  - **LLM-разбор, привязанный к фактам:** код формулирует ≤3 факта ошибки литералом, модель дописывает к каждому
    одно предложение «к чему приведёт и как отработать»; грамматика из фактов, фильтры: повторы, обрезка,
    `grounded` (выкидывает пункт с числом или цитатой, которых нет на входе), только кириллица. Нет модели → блок
    «недоступно», текст по правилам не подменяется. §9, `DebriefWriter`/`DebriefHandler`.
  - **Модель Раша (JMLE)** для эмпирической сложности сценариев и способности обучаемых на одной шкале и
    **симулятор когорты**, который генерирует только поведение и гонит его через боевой API и оценщик (истинные
    параметры сохранены, чтобы проверить восстановление). `src/main/java/ru/lct/arm112/service/analytics/RaschService.java`,
    `src/test/java/ru/lct/arm112/golden/CohortSimulator.java`, `history/2026-09-23-2-cohort-simulator.md`.
  - **Грамотность без ложных срабатываний:** LanguageTool + свои правила (смешение латиницы и кириллицы, тройная
    буква, Левенштейн 1 к топониму); белые списки из сценариев: улицы, ФИО, аббревиатуры служб; отключены
    TYPOGRAPHY/STYLE на телеграфном стиле. Принцип «ложное замечание дороже пропуска». §3.6.
  - Справочники из ПОВ-112: «Что случилось?» (49 позиций) с опросными картами и выводом типа ЕКП из ответов,
    216 служб с районными и окружными ДДС, матрица ЕКП → службы, улицы из ГАР; 96 билетов кейса как сценарии.
    `src/main/resources/seed/` (survey-trees.json, service-matrix.json, services.json), `docs/materials/`.
- **Слабые места / чего нет:** нет голоса и разговора — звонок/доклад — это кнопка и состояние; классификатор
  типа по тексту слабый (top-1 35 %) и показан только подсказкой; сценарий TRAINEE_MADE оценивается по эталону
  базового билета, а не по тому, что увидел диспетчер.
- **Куда смотреть следующему агенту:** `docs/assessment/ASSESSMENT_AND_SCENARIOS.md` (вся оценка одним документом),
  `docs/assessment/DASHBOARDS.md` (экраны разбора преподавателя и обучающегося), `history/` (журнал решений с «почему»).

### andrewgein/lct-simulator112 — https://github.com/andrewgein/lct-simulator112
- **Команда:** не указана · **создан / последний коммит:** 15.09 / 29.09 · **коммитов:** 643 (≈220 PR) ·
  **стек:** 11 микросервисов на Java 21/Spring Boot (gRPC, Kafka, Redis, MinIO, PostgreSQL по базе на сервис,
  гексагональная архитектура), dialog-service на Python/FastAPI (Vosk → LLM qwen3:4b-instruct через
  OpenAI-совместимый API → F5-TTS **на GPU**), MLServer с rubert-tiny-bilingual-nli, Astro SSR + Preact +
  Web Awesome, Prometheus/Grafana/Loki; стенд sim-112.online; внешние API: Nominatim, 2ГИС MapGL, DaData
- **Скоуп:** оба (`SYSTEM_112` и `DDS`) · **зрелость:** полноценное, но тяжёлое: не офлайн и не без GPU
- **Суть:** «курс → задание → уровень» как в LMS, с сертификатом при >50 %. ДДС — линейная шкала этапов,
  которую задаёт преподаватель: на каждом этапе «фактический статус» и звонки бригаде или другой службе;
  ученик ставит статусы сам, а сверка своевременности идёт только на разборе.
- **Интересное для нас:**
  - **Модель сценария ДДС «этапы с фактическим статусом».** Этап: тип (ASSIGN_BRIGADE /
    WAIT_FOR_BRIGADE_STATUS_CHANGE / CALL_BRIGADE_FOR_STATUS / REQUEST_ADDITIONAL_SERVICE / COMPLETE_INCIDENT),
    лимит времени, звонки (входящий доклад или исходящий), ожидаемый комментарий, фактический статус после
    этапа, условия завершения TIME / STATUS / CALLS по «ИЛИ», опция `failOnTimeout`. Статус, выставленный
    учеником, хранится отдельно; правильный = совпал с фактическим и выставлен в окне «от смены до конца
    следующего этапа». Во время уровня ученика не блокируют. `backend/incident-service/src/main/java/com/simulator112/incident/domain/dds/DdsStage.java`,
    `backend/review-service/.../domain/evaluation/DdsReviewRubric.java`, обоснование — `frontend/docs/dds-requirements.md`.
  - **Разбор чата кейсодержателя с номерами сообщений** (подтверждено / интерпретация / открыто): ДДС не добавляет
    службы в карточку, бригада сама статусы не меняет, на приёмке нужны голос ДДС ↔ вышестоящий начальник и
    ДДС ↔ руководитель бригады, карточки приходят параллельно, у ДДС нет своей опросной карты. Полезно сверить
    с нашим Q&A. `frontend/docs/dds-requirements.md`, `frontend/docs/task-requirements.md`.
  - **Промпты LLM для бригады и «другой службы» по направлению звонка**: входящий доклад (бригада начинает
    сама) или исходящий (ждёт реплику диспетчера); приоритет «прощание → вопрос → приветствие → переспрос»;
    «не придумывай время, статус, событие»; адрес — полными словами для TTS. Длинный промпт заявителя:
    ограниченное знание, постепенное раскрытие, скрытые факты по условию, три типа реакции на перебивание.
    `backend/dialog-service/app/application/model/prompts.py`.
  - **Комментарий диспетчера проверяется NLI**: rubert-tiny-bilingual-nli (MLServer) сверяет комментарий
    с `expectedComment` этапа (20 из 100 баллов); остальные 80 делятся поровну между проверками
    «статус вовремя» и «звонок состоялся», с честным распределением остатка.
    `backend/review-service/README.md`, `adapter/out/mlserver/MlServerDialogueAnalysisAdapter.java`.
  - **Запись звонка в MinIO и прослушивание на разборе** у ученика и преподавателя (карточка + запись +
    баллы; преподаватель правит баллы по критериям и комментирует, ученику приходит письмо и уведомление).
    `docs/reviewer-test-scenario.md` шаги 11 и 15.
  - **Эмоции голоса заявителя:** 5 профилей (calm/worried/panicked/aggressive/confused) с референс-текстами
    для клонирования F5-TTS. `backend/dialog-service/resources/voices/manifest.json`.
  - ИИ-помощник в конструкторе сценария: описал инцидент текстом → форма заполнилась (Ollama).
- **Слабые места / чего нет:** F5-TTS требует GPU, адреса и карты — через внешние API, 11 сервисов + Kafka
  для хакатонного объёма; оценка ДДС не учитывает решение «принять / не принять» по компетенции; физической
  IP-телефонии и звонка начальнику нет (сами признают).
- **Куда смотреть следующему агенту:** `frontend/docs/dds-requirements.md`, `backend/incident-service/src/main/java/com/simulator112/incident/domain/dds/`,
  `backend/dialog-service/app/application/model/prompts.py`.

- **Скоуп:** ДДС (как у нас): обучаемый — диспетчер ДДС, «ИИ-оператор 112» выдаёт готовую карточку, доклад
  «ИИ-руководителю» · **зрелость:** прототип с проработанным ИИ-контуром; модуль `ai/` (441 тест) с UI
  связан слабо: фронт умеет работать на моке в localStorage, голос в браузере — speechSynthesis + Web Speech API.
  `USER_GUIDE.md` местами обещает больше, чем видно в коде.
- **Суть:** самая близкая к нам постановка в группе. Сильная сторона — архитектура доверия к оценке (статусы
  критериев, evidence, снимок версий попытки, «сбой модели ≠ ошибка ученика») и ИИ-руководитель как конечный
  автомат с LLM только для формулировки.
- **Интересное для нас:**
  - **ИИ-руководитель = автомат «выслушать → уточнить → повторить понятое (read-back) → подтвердить получение»,**
    не больше 2 уточнений на элемент. Доклад разбит на элементы: суть / место / обстоятельства / решение ДДС /
    что требуется от руководителя; у каждого паттерны по основам слов. LLM лишь перефразирует реплику внутри уже

## Топ-находки группы

1. **LLM только на подготовке, а в разговоре CPU-классификатор интентов и заранее озвученные реплики:**
   E5-small INT8 + T-one + Piper, без GPU и без галлюцинаций в рантайме; преподаватель утверждает
   сценарий после озвучки (BlusteryS/Training112).
2. **Статусы ДДС открываются докладами по телефону:** бригада звонит → только тогда ставится следующий статус;
   руководитель согласует выезд или отказывает; бригада сообщает «адрес не совпадает» → звонок в 112. Альтернатива —
   сценарий как шкала этапов с «фактическим статусом» и сверка своевременности только на разборе
   (BlusteryS/Training112; andrewgein/lct-simulator112).
3. **ИИ-руководитель как автомат «выслушать → уточнить → повторить понятое → подтвердить»:** доклад разбит на
   элементы (суть / место / обстоятельства / решение ДДС / что нужно от руководителя), LLM только перефразирует
   реплику внутри выбранного действия (fluffb4ll + kEzorka, «67-420»).
4. **Доверие к автооценке:** статусы критерия `not_checked` / `no_evidence` / `technical_error` вместо нуля,
   evidence (event_ids) у каждого вердикта, снимок версий попытки, правка преподавателя — новая версия балла;
   калибровка ИИ по ≥30 оценкам преподавателя с отложенной выборкой (67-420; Dema-koder; Training112).
5. **Дешёвые правила оценки ДДС:** детектор «прокликивания» статусов, ожидаемое «Принять / Не принять»
   выводится из службы обучаемого, «Отказ» без «Прибытия» — штраф, «липкие» просрочки; интенсивность потока
   карточек (LOW / MEDIUM / HIGH + фоновые карточки) как рычаг сложности (Dema-koder/lct2026-arm112).
6. **Нормативка и голос заказчика:** неформальные ответы заказчика от 27.09 и свод нормативов ПП РФ № 1931 со
   ссылками (DanK1-PRO/Hakaton-2026); разбор чата кейса с номерами сообщений (andrewgein, `frontend/docs/dds-requirements.md`).
