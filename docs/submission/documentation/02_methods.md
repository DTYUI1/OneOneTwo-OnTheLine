# 2. Методы обработки данных

Все формулы реализованы в коде и покрыты тестами; ссылки указывают на файлы репозитория.

## 2.1 Классификатор и маршрутизация

`packages/evalcore/evalcore/classifier.py` читает CSV классификатора (3 строки шапки),
определяет редакцию по заголовку столбца 12 («Главная служба» — 046_24, «Сценарий
реагирования» — 046_11) и проверяет, что каждая колонка служб принадлежит своей группе
(МЧС, МВД, СМП, МОСГАЗ, Мослифт, ЖКХ). Правило оповещения = (тип, служба, условие, текст).
Условие получает стабильный признак `trigger` (`default`, `no_access`, `offense`, `victims`,
`victims_off_site`, `gasification`), потому что номера колонок в редакциях различаются.
Пустая ячейка и «нет реагирования» правил не создают.

## 2.2 Сценарии и эталоны

- **По билетам заказчика** (`scripts/build_ticket_scenarios.py`): ситуация и адрес переносятся
  вручную со скана PDF (OCR — только для поиска), тип и службы — по 046_24, эталон — по
  памятке ДДС. В `data/ticket_scenarios/manifest.json` сохраняются билет, задача, страница,
  дословный текст, версия классификатора и основание эталона; `teacher_review = not_reviewed`.
  Телефоны заявителей заменены учебными. Тест проверяет, что эталонное прохождение получает
  полный балл по маршруту, статусам и адресу.
- **Генератор** (`evalcore/scenario.py`): конструктор (тип × адрес × пострадавшие × осложнения ×
  уровень × вес × seed) → карточка и эталон детерминированно; один seed — один результат.
  Службы — основная служба типа и правила классификатора по `trigger`. ИИ-нарратив не меняет
  эталон и получателей.
- **Утверждение**: эталон проверяется перед утверждением (`evalcore/validation.py`) —
  допустимая цепочка статусов, решение, получатель перенаправления, адресат обязательного звонка.

## 2.3 Оценка по правилам

`evalcore/scoring.py`: итог = Σ(wᵢ·sᵢ) / Σwᵢ по семи критериям и двум критериям комментария
(если их вес есть в снимке занятия); при критической ошибке итог не выше `critical_cap`
(по умолчанию 0,5). Веса и нормативы — из снимка занятия.

| Критерий | Балл sᵢ | Критическая ошибка |
|---|---|---|
| reaction_time | 1 при t ≤ N, иначе max(0, 2 − t/N); t — реакция I-TIME v3 (направление → первое «Принята/Не принята»), N = 30 с | нет |
| handling_time | та же шкала для активной обработки v3 (первое открытие → завершение минус подтверждённое ожидание), N = 180 с | нет |
| status_flow | LCS(эталон, факт) / max(длин) по последовательности статусов | нет |
| routing | 1 при совпадении цепочки решений и адресата перенаправления, иначе 0 | да |
| required_fields | доля заполненных обязательных полей | нет |
| address | доля компонентов ручного адреса диспетчера (город, улица, дом, корпус, квартира), совпавших с эталоном после нормализации (регистр, «ё», «г.», «ул.», «д.», «корп.», «кв.»); похожая другая улица не засчитывается; без ручного адреса — поиск в комментарии («ул.»/«улица» не различаются, номер дома — после «д.»/«дом» или сразу за улицей: «Дубнинская улица, 1») | да, если ошибка в улице или доме |
| call | лучшее среднее по звонкам: соединение, адресат, звонок до срока | по эталону |
| spelling | 1 − ошибки / max(4, слова / 5); пустой обязательный комментарий — 0 | нет |
| comment_keywords | доля найденных пунктов: адрес, суть происшествия, решение, пострадавшие, слова эталона | нет |

Время в критериях считается тем же расчётом, что в разборе и на экранах (раздел 2.5), по
методике из снимка занятия; для старых занятий — по их версии. Маршрутизация: исправленная
«Не принята → Принята» в принятом сценарии не считается ошибкой маршрута.

**Критерии комментария (28.09, Q&A Q10, FR-4.2)** — `evalcore/comment.py`, проверка текста —
`apps/api/app/core/spelling.py`; без ИИ и без сети. Вес по умолчанию: грамотность 0,5,
ключевые сведения 1. В занятиях, созданных раньше, весов нет — критерии не считаются, итоги
прежние.

- *Грамотность.* Слово верно, если оно есть в морфологическом словаре OpenCorpora
  (`pymorphy3`, все формы слова), в словаре 112 (`spelling_112.txt`: «Росгвардия»,
  «спецтранспорт», «пр-т»…) или в названиях улиц (справочник и адрес сценария). Не проверяются
  слова короче трёх букв, сокращения из заглавных (ДТП, ГИБДД) и слова с заглавной не в начале
  предложения — имена и названия. Варианты исправления — слова словаря на расстоянии одной
  правки (пропуск, лишняя буква, перестановка, замена; дешевле пропуск и соседняя клавиша) и
  разбиение слитного написания. Прогон по всем текстам `data/`: из 2103 разных слов словарь
  не знал 86, большинство — настоящие опечатки исходных данных; ложные срабатывания внесены
  в словарь 112.
- *Ключевые сведения* — те же пункты, что у ИИ-судьи (раздел 2.4), но по словам в начальной
  форме: улица — без исправления опечаток («Дубнинская» ≠ «Дубининская»), номер дома — после
  «дом», «д.» или сразу за улицей; суть — половина значимых слов класса происшествия; решение
  — слова направления сил или отказа; пострадавшие — если они есть в карточке; свои слова
  преподаватель задаёт в студии (`reference.comment_keywords`, варианты через «/»).
  Опечатка в остальных словах пункт не отменяет — за неё снижается грамотность.
- *Подсказки в АРМ.* Галочка «Подсказки орфографии» в настройках занятия (по умолчанию
  выключена, в самостоятельной практике включена): под комментарием подчёркиваются ошибки и
  предлагаются исправления той же проверкой (`POST /spelling/check`). Обучаемому — только в
  своём занятии с включённой галочкой.

## 2.4 ИИ-оценка комментария

`apps/api/app/worker/judging.py`, провайдер `providers/judge/local_llamacpp.py`, модель
Qwen3-4B-Instruct-2507 Q4_K_M через llama.cpp (CPU):

1. Из карточки и решения эталона формируются ключевые факты: адрес (улица, дом), суть
   происшествия, принятое решение или причина отказа, пострадавшие. Текст эталона модели
   не передаётся.
2. Модель получает факты и комментарий обучаемого **как данные** (поле JSON; инструкции внутри
   игнорируются), возвращает по JSON Schema раскладку фактов на найденные/отсутствующие,
   понятность 0–1 и пояснение на русском; temperature 0.
3. Ответ отклоняется (оценка остаётся по правилам, статус partial), если факт выдуман, пропущен
   или повторён, ответ вне схемы или истёк таймаут (120 с). Найденный факт без опоры в тексте
   (общая основа слова; для адреса — номер дома) считается отсутствующим.
4. Полнота = найденные / все факты; llm = (полнота + понятность) / 2.
5. **Итог = 0,8 · rules + 0,2 · llm**, при критической ошибке — не выше `critical_cap`.
6. Обратная связь: до трёх последних решений преподавателя по тому же сценарию, созданных
   **до** текущей оценки, передаются как примеры; их ID сохраняются. Старые оценки не
   переписываются, будущие результаты не используются.

Замер на CPU (4 потока): 15–27 с на комментарий; полный комментарий — 1,0/1,0; «Горит что-то,
выехали» — 0,0/0,3; попытка инъекции не выполняется (`docs/C06_JUDGE_REPORT.md`).

## 2.5 Учебное время (I-TIME v3)

`evalcore/timing.py` и тот же алгоритм в браузере (`apps/web/src/shared/timing.ts`) проверяются
42 общими числовыми примерами (`contracts/examples/timing-v2.json`, `timing-v3.json`).

- **Направление** карточки в ДДС фиксирует сервер (момент выдачи worker).
- **Реакция** = направление → первый статус «Принята/Не принята»; норматив 30 с (памятка ДДС).
  Открытие карточки реакцию не закрывает.
- **Полная обработка** = первое открытие → завершение (работы завершены, отказ от работ,
  перенаправление, окончательная «Не принята»).
- **Ожидание** — объединение подтверждённых интервалов ожидания учебного сообщения бригады
  (от ответа на звонок до выдачи реплики) внутри обработки.
- **Активная обработка** = полная − ожидание; норматив 180 с сравнивается с активной.
- Пример: направление 0, открытие 20, «Принята» 40, завершение 190 → реакция 40 (превышение),
  полная 170, активная 170; при ожидании 60 с активная 110.
- Отсутствующее событие даёт `null` и аномалию, а не ноль; отрицательный интервал — `invalid`.
  Превышение отмечается только при достоверном измерении.

**Синхронизация часов** (метод midpoint): клиент шлёт ping с `client_sent`, сервер сохраняет
момент получения и отвечает тем же `server_at`; клиент фиксирует `client_received` и
подтверждает образец. Поправка = server_at − (client_sent + client_received)/2, проверка
формулы ±1 мс, RTT ≤ 2 с, возраст образца ≤ 60 с. Время действия = client_ts + поправка;
если оно в будущем (> +250 мс) или задержка буфера > 30 с — берётся время сервера с отметкой
«оценочно». Проверенное время даёт качество `verified`, иначе `estimated`.

## 2.6 Прогноз и аналитика

- **Прогноз до попытки** сохраняется при выдаче карточки: IRT-1PL P = 1/(1+e^−(θ−b)),
  b = (вес − 5,5)/2,25, ожидаемое время = N·(1,35 − 0,7·P) (`worker/scheduler.py`,
  модель `worker-irt-fallback-v1`); факт дописывается один раз после завершения.
- **Рекомендация уровня** (`evalcore/adaptive.py`, `rules-v1`): по пяти последним завершённым
  попыткам — средний итоговый балл (с учётом решения преподавателя), критические ошибки и
  подтверждённое время. Балл ≥ 0,8 без критических ошибок и превышений — повысить уровень и вес
  на шаг; балл < 0,6, две попытки с критическими ошибками или большинство превышений — понизить;
  иначе оставить. До трёх попыток — холодный старт. Основание выдаётся словами.
- **Разбор попытки** (`GET /cards/{id}/analysis`): статус попытки, время v3, слои оценки
  (обязательны rules и llm; невыполненные помечены с причиной), переопределение преподавателя,
  счётчики ошибок (`null` — не проверено, 0 — ошибок нет), прогноз и факт.
- **Аналитика занятия**: по каждому обучаемому — попытки, оценённые, средний итоговый балл,
  средние реакция и обработка **только по проверенным измерениям** с числом наблюдений.
