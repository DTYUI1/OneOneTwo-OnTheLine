# Ночной прогон связности мира

Инструкция для облачного агента, который ночью проверяет, что мир тренажёра диспетчера ДДС связен.
Связен значит, что бригада не говорит «выезжаем» после «выехали», не задаёт вопрос из дороги с места,
не говорит поверх своего вопроса, а служба не оказывается на месте без вызова. Поводом стала проверка
17.10: сценарии чинили по одному, и каждая точечная правка открывала соседнюю несостыковку.

Главное правило: **несостыковку чинят в движке для всего класса, а не в одном сценарии.** Сценарий
правят, только когда линтер нашёл в нём настоящую ошибку данных.

## Что запускать

Нужен PostgreSQL с правом `CREATE DATABASE`, например тестовый контейнер. Прогон один раз
готовит засеянную базу-шаблон `arm112_coherence_…` (alembic и `app.seed`), каждый процесс пула
берёт её копию (`CREATE DATABASE … TEMPLATE`), в конце все базы прогона удаляются. Стенд и
учётные записи обучаемых прогон не трогает.

Команда одна — и перед коммитом, и ночью: все сценарии × все ветки × все политики.

```sh
cd apps/api
COHERENCE_DATABASE_URL=postgresql+asyncpg://t:t@127.0.0.1:55471/t \
  uv run python -m app.tools.coherence --out tmp/coherence/report.md
```

- Код выхода 0 — нарушений нет. 1 — есть нарушения или прогон упал.
- Правило можно пометить «ждёт решения пользователя» (`Invariant.pending`): его нарушения стоят
  в отчёте отдельной таблицей и код выхода не меняют. Сейчас таких нет: последнее,
  `called_service_unvoiced` (сценарии без записанных фраз о совместной работе с вызванной
  службой, HQ-055), снято с записью bank-v9 — молчание о вызванной службе теперь нарушение
  `called_service_ignored` во всех сценариях. Фраза, написанная под реплику сценария, встаёт в
  него только с записью: план «сценарий → доклад → id фразы» — `scripts/voices/bank/placements.json`,
  после записи набора bank-vN его ставит `scripts/voices/bank/place.py`.
- Переменную `COHERENCE_DATABASE_URL` можно не задавать, если задана `DATABASE_URL_TEST`.
- 37 сценариев, 681 проход, процессов по числу ядер (`--jobs`). На ноутбуке разработчика с
  базой в Docker — около 5 минут; упирается в базу (4 ядра виртуальной машины Docker).

Полезные ключи:

- `--only lift-stuck-101-1 gas-entrance-104-2` — только эти сценарии.
- `--policy эталон readback` — только эти политики; `readback` берёт все ветки события.
- `--all` — расшифровки всех прогонов, а не только прогонов с нарушениями.
- `--scenarios путь` — другая папка сценариев (по умолчанию `data/scenarios`).

## Проверка сценария из кода (генератор)

Генератор карточек (HQ-027) проверяет сценарий до выдачи без файла в `data/scenarios`:
`check_scenario` из `app.tools.coherence.check` принимает словарь в формате файла сценария
(`contracts/scenario-file.schema.json`) и возвращает список нарушений. Пустой список — сценарий
связен.

```python
from app.tools.coherence.check import StandError, check_scenario

try:
    found = check_scenario(
        scenario,                   # dict в формате data/scenarios/<code>.json
        database="postgresql+asyncpg://t:t@127.0.0.1:55471/t",  # с правом CREATE DATABASE
        policies=None,              # все политики; или ["эталон", "readback"]
        jobs=4,                     # рабочих процессов; по умолчанию 1
        timeout=900,                # с на один рабочий процесс; по умолчанию 900
    )
except StandError as error:
    ...                             # сбой стенда: модели не отдавать, повторить позже
for item in found:
    # {"rule": "stage_regress", "policy": "caller-phone:late", "at": 75.0,
    #  "detail": "«Понял, выезжаем на адрес.» — «выезжаем»: …",
    #  "line": "Бригада 1: Понял, выезжаем на адрес.", "failing": True}
    ...
```

- Сначала сценарий проходит загрузчик каталога: схему, ссылки и линтер
  (`app.seed.scenarios.validate`). Если есть ошибка, вернётся одно нарушение
  `{"rule": "lint", "policy": None, …}`, а в `detail` будет текст загрузчика. Линтеру база не
  нужна (справочник служб — `data/phonebook.json`), ответ приходит сразу, без сборки шаблона.
- Иначе сценарий записывается под своим UUID в копию засеянной базы-шаблона и проходит
  через движок по всем веткам и политикам или по выбранным в `policies`. Политики называются
  так же, как в `--policy`.
- В каждом нарушении есть класс (`rule`, см. каталог ниже, а также `run_failed`), политика
  (ветка), секунда от прихода карточки, описание и реплика, которая звучала в этот момент
  (`line`). Если `failing` равно `False`, правило ждёт решения пользователя: такое нарушение
  не ошибка, а только сведения.
- Нарушения можно вернуть модели как есть, чтобы она сделала вторую попытку.
- **Нарушение или исключение.** Нарушение (элемент списка) — про сценарий: `lint`, инвариант
  или `run_failed` — движок упал на данных этого сценария (исключение в проходе или в проверке
  инвариантов, сценарий не записался в базу). `run_failed` одной политики не отменяет
  нарушений других. Сбой стенда — исключение `StandError` с понятным текстом, его модели не
  отдают: PostgreSQL недоступна или оборвала соединение (в цепочке причин — ошибка
  соединения, пропавшая база или таймаут в драйвере БД), шаблон не собрался, копия шаблона
  не создалась, приложение прогона не поднялось или не остановилось, рабочий процесс упал
  без ответа или не ответил за `timeout` секунд (тогда его останавливают). Ошибки данных
  запроса (`asyncpg` `DataError`, `ClientConfigurationError`) и таймаут в логике движка —
  `run_failed`, не стенд. Копии базы этого вызова удаляются и после `StandError`. Шаблон, удалённый другим
  процессом (`CREATE DATABASE … TEMPLATE` не находит его), собирается заново один раз; не
  вышло — `StandError`.
- Шаблон базы `arm112_coherence_tpl_<хеш>` собирается один раз на содержимое кода и данных.
  Первый вызов в новом коде занимает около минуты, следующие вызовы и другие процессы берут
  готовый шаблон. Один проход занимает 3–10 с; все ветки сценария на 4 ядрах — 1–2 минуты.
- Функция синхронная. Из async-кода её вызывают через `await asyncio.to_thread(check_scenario, …)`;
  одновременные вызовы из разных потоков не мешают друг другу.
- Проходы всегда идут в рабочих процессах `python -m app.tools.coherence.check_worker` (запрос
  и ответ — JSON через stdin/stdout), и при `jobs=1` — один процесс. Прогон подменяет часы
  (`datetime`) в модулях `app.*`; в процессе вызывающего (API, генератор) это сбило бы его
  время. Защита `if __name__ == "__main__":` у вызывающего скрипта не нужна. При `jobs > 1`
  проходы делятся между процессами по длине; запуск процесса — около 2 с.

В подписи варианта ответа (`reply_options[].label`) генератор ссылается на поле карточки,
а не повторяет его. Есть три поля: `{caller_phone}`, `{caller_name}` и `{address}`
(`contracts/scenario-events.md`). Значение подставляет загрузчик. В репликах подстановки нет,
потому что их текст должен совпадать с озвучкой. Неизвестное поле — ошибка линтера.
На кнопке `{caller_phone}` — номер группами («+7 900 000-07-14»), `{caller_name}` — «Фамилия
Имя» (отчество есть в карточке). Голосом (`evalcore.voice_reply`) подставленное поле — одно
необязательное слово подписи: телефон сверяется по цифрам (числа словами, «8» вместо «+7»,
любые разделители; хватает последних 4–7 цифр), ФИО — по фамилии в любом падеже. Прозвучавшее
поле само решает вариант; без него хватает остальных слов («Телефон заявителя», «Телефон в
карточке»); другой номер вариант не засчитывает.

### Уровни 3–4 (решение 17, 18.10)

- **Уровень 3:** два события с ветками. Первое — ловушка повтора адреса (`readback_error`),
  второе — вопрос бригады (`clarify`) или просьба о службе (`request_service`).
- **Уровень 4:** всё, что на уровне 3, и ещё тревога (`alarm`) или молчание бригады
  (`silence`).

## Как это устроено

Код лежит в `apps/api/app/tools/coherence/`.

- `harness.py` — настоящее приложение в процессе (ASGI через httpx), база-шаблон и сдвигаемые
  часы: модули `app.*` видят время симуляции. Распознавания речи нет: фразы диспетчера
  отправляются текстом. Реальных ожиданий нигде нет.
- Часы прыгают: тик worker идёт, только когда мир может измениться сам (`runner._world`).
  Когда — говорит движок: `due_firings` и `report_schedule` на час вперёд, сроки вызовов и отдела
  контроля. Если срок наступил, а тик ничего не меняет (доклад готов, бригада занята), — проба тика
  в откатываемой транзакции с удвоением шага. Расшифровка та же, что при тике каждую секунду
  (`ScenarioRun(..., skip_idle=False)`): если правите `_next_change`, сверьте их на паре сценариев.
- `runner.py` — модель обучаемого и окна телефона. Она принимает карточку, даёт вводную, слушает
  доклады, ставит статусы, отвечает бригаде и звонит в службы. Правила окна телефона (представление,
  «Как приняли?», тихий отбой) повторены по `Softphone`, длительности реплик взяты из манифестов
  банка фраз (`phone.py`).
- `policies.py` — как ведёт себя обучаемый:
  - эталон;
  - каждая ветка каждого события (`<событие>:met`, `:late`, `:wrong`, `:missed`, у просьбы о
    службе ещё `:already`, `:surprise`, `:told`);
  - человеческие отклонения: медленно отвечает, не берёт трубку, кладёт трубку после доклада,
    не подтверждает, ставит статус сразу или медленно, отвечает не то, молчит, не звонит бригаде,
    даёт неверный адрес, не сообщает бригаде о вызванной службе, сообщает с удержания
    (`сообщает_с_удержания`: бригада на удержании, звонок в службу, возврат на линию —
    «Отправил, ждите» без названия службы), сообщает во время звонка в службу
    (`сообщает_во_время_звонка_в_службу`: служба ответила — она на удержании, к бригаде:
    «Отправил, ждите», срока вести ещё нет; потом снова служба и доклад), уточняет с удержания
    (`уточняет_с_удержания`, HQ-058: на вопрос бригады с вариантами ответа — удержание, звонок
    живому заявителю (коротко: просьба подойти и прощание) или в службу из просьбы бригады,
    снятие с удержания, ответ на повторённый вопрос; вопрос в сроке — бригада повторяет его и
    придерживает новость до ответа или срока, срок истёк — «на связи» и новость; только
    сценариям, где есть вопрос и кому позвонить), поправляет повтор адреса фразой
    (`поправляет_фразой`, HQ-024: на повтор с ошибкой — «Понял», следом `brigade_said`
    «Нет, <адрес карточки>.»; `поправляет_фразой_доложите` — «<адрес карточки>, доложите по
    прибытии.»; бригада отвечает один раз — репликой ветки `met`, окно телефона молчит
    (`world_answers` распознавания, `scenario_events.phrase_fixes_readback`); только
    сценариям с ловушкой повтора адреса).
  - Сценарий с живым заявителем (блок `caller`, HQ-019): ответив бригаде на её вопрос, диспетчер
    звонит заявителю (номер 458 роли «Заявитель» в телефоне ДДС занятия) — где он, когда
    подойдёт (до полного ответа), просьба подойти, прощание — текстами кнопок окна из таблицы
    сюжета (`scripts/voices/bank/callers/plots/`); заявитель понимает фразу и отвечает по
    правилам окна телефона (`caller.py` — зеркало `softphone/caller/hearing.ts` и
    `conversation.ts`, общие таблицы примеров `hearing.cases.json` и `conversation.cases.json`
    проверяют vitest и pytest) и каждая его реплика уходит отметкой `caller_said`. Класс
    «звонок заявителю»: `заявитель_растерянная` (преподаватель сменил характер у абонента —
    уточняет срок) и `заявитель_молчит` (молчит в трубку: «Алло, вы тут?» дважды, отбой
    заявителя, перезвон — «это опять вы?»).
  - Ветка met без вводной отдельно не гоняется — её проходит эталон.
  - Вызвав службу по просьбе бригады, диспетчер сообщает ей, что служба едет (решение HQ-055).
    Бригада отвечает «Понял, ждём» как окно телефона — только в окне вести сервера (после
    набора номера службы и до её приезда, `delivery.service_called_at`/`news_by`).
- `transcript.py` — расшифровка: кто, когда и что сказал, и откуда взялась реплика (доклад плана,
  событие, ветка, подмена, повтор адреса).
- `invariants.py` — каталог правил (ниже) и проверка расшифровки.
- `night.py` и `__main__.py` — пул процессов, отчёт и код выхода.

Линтер сценариев — `apps/api/app/seed/scenario_lint.py`, словарь этапов и служб —
`apps/api/app/seed/world_lexicon.py`. Линтер работает в двух местах:

- при загрузке сценариев (`app.seed.scenarios`): несвязный файл не попадает в базу, загрузчик
  называет причину по-русски;
- в CI: тест `apps/api/tests/test_scenario_lint.py` проверяет весь каталог.

## Каталог инвариантов

| Правило | Что проверяет |
|---|---|
| `stage_regress` | Реплика не противоречит этапу бригады: после выезда не «выезжаем», на месте не «разворачиваемся», в пути не «поднимаемся» |
| `event_after_next_report` | Событие, сработавшее после доклада X, звучит до следующего доклада плана: вопрос из дороги не задаётся с места |
| `answer_after_target` | Ответ ветки не звучит после доклада, который событие держит или подменяет |
| `talks_over_question` | Бригада не говорит дальше, пока ждёт ответа на свой вопрос или «Как приняли?»: до ответа или паузы 8 с |
| `duplicate_meaning` | Нет двух реплик подряд об одном, например «выезжаем» дважды |
| `service_uncalled` | Служба на месте только после вызова диспетчером или 112 по карточке |
| `service_too_early` | Служба на месте не раньше, чем доехала (20 с после вызова) |
| `called_service_ignored` | Вызванная по просьбе служба — в разговоре дальше: бригада «Понял, ждём скорую» на весть диспетчера (не сообщил — «подъехала, могли бы и сказать»), доклад после — о совместной работе (HQ-055) |
| `deadline_eaten` | Срок реакции на событие не съеден системой (звонок, представление, сама реплика) больше чем на четверть |
| `answered_twice` | На одну фразу диспетчера бригада отвечает один раз: окно телефона («Принял», «Понял, ждём скорую») или ответ ветки мира, не оба подряд (HQ-024); ветки, которые бригада говорит сама (`surprise`, `missed`), и повтор доклада на «Доложите» — не такие ответы |
| `overlapping_speech` | Реплики одного разговора не звучат одновременно |
| `confirm_misplaced` | «Как приняли?» звучит только после доклада во входящем вызове |
| `callback_without_news` | Бригада не перезванивает только ради ответа-подтверждения (ветки met, late, already): о службе ей сообщает диспетчер (HQ-055); повторная просьба и «внезапный» приезд службы — повод позвонить |
| `confirm_unanswered` | Эталон отвечает «Принял» (`report_confirmed`) на каждое «Как приняли?» — в том числе переспрошенное после удержания и при позднем ответе службы (решение капитана 18.10, HQ-058) |
| `line_twice` | Реплика сценария не звучит дважды |
| `not_closed`, `status_refused` | Карточку можно закрыть: статус ставится после доклада, доклад приходит |
| `report_wait` | Доклада не ждут дольше 40 с не по своей вине (эталон и ветки) |
| `caller_line` | Живой заявитель (HQ-019): сервер принял каждую его реплику (`caller_said`), «Алло, вы тут?» — только после 8 с тишины диспетчера |
| `run_failed` | Прогон упал: это тоже находка |

## Что отвергает линтер

- Слово другого этапа в докладе, реплике события, ответе ветки или подмене. Пример: «поднимаемся»
  в ответе на вопрос, заданный из дороги.
- Повтор адреса с ошибкой (`readback_error`) не на докладе о выезде.
- Последствие события (задержку или подмену) для доклада, который звучит не позже триггера: уже
  сказанное не отменить.
- Службу «на месте», когда диспетчеру не предложено её вызвать. Такой доклад нужно держать
  событием «просьба о службе» и подменять в ветке missed.
- Службу, вызванную по просьбе бригады, о которой бригада больше не говорит: доклад после просьбы
  должен упомянуть совместную работу с ней. Исключений нет.
- Доклад, который ждёт статуса, а этот статус не обосновывает ни один доклад.
- Событие, исход которого наступает позже 40 с ожидания доклада.
- Фразу, которая звучит в сценарии дважды.

## Если ночь нашла нарушения

1. Откройте отчёт: сверху сводка по классам, ниже нарушения по прогонам и расшифровки.
2. Найдите класс. Если нарушений одного правила много в разных сценариях, это правило движка,
   а не ошибка данных.
3. Чините там, где рождается класс:
   - `apps/api/app/api/training/scenario_events.py` — когда событие срабатывает и что делает мир;
   - `apps/api/app/api/training/turns.py` — очередь реплик бригады;
   - `apps/api/app/worker/training.py` — порядок выдачи;
   - `packages/evalcore/evalcore/brigade.py` — сроки и исходы;
   - `apps/web/src/arm/softphone` — правила окна телефона, их зеркало в `phone.py`.
4. Если сломан один файл сценария, сначала добавьте правило в линтер, чтобы оно ловило эту ошибку
   во всех файлах, и только потом правьте данные.
5. Если правило противоречит вкусу (что бригада говорит, как звучит разговор), не решайте за
   пользователя. Запишите развилку одной строкой противоречия и пометьте правило `pending`.

Перед каждым коммитом должны быть зелёными:

- `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy`;
- тесты затронутых областей (`uv run pytest -n 8 …`);
- если тронут веб-клиент — `pnpm lint`, `pnpm typecheck`, `pnpm test` в `apps/web`;
- если тронут движок мира — прогон связности (команда выше).

Не трогать:

- голосовые данные (`data/voices`, `scripts/voices`); фразы не синтезировать, а перечислить
  нужные тексты в отчёте;
- стенд и учётные записи обучаемых;
- существующие файлы в `docs/`.

Контракты (`contracts/`) меняются только отдельным коммитом `contract: …`. Не пушить и не
сливать ветки без просьбы пользователя.

## Решено пользователем
