## Билеты: что теперь известно

Каждый билет содержит задание «Отработайте вызовы от заявителя» и таблицу
«№ / Ситуация / Адрес». В ситуациях есть данные заявителя, признаки происшествия,
пострадавшие и другие вводные; местами в скобках приведены уточнения адресов.

Это исходные условия упражнений. В PDF нет размеченного набора:
«полностью заполненная карточка 112 → назначенная ДДС → правильные действия →
звонки → статусы → комментарии → оценка». Заголовок относится к обработке вызова
заявителя; он не отменяет уточнение Q&A о роли обучаемого в нашем прототипе — ДДС,
получающая готовую карточку.

96 — количество позиций задач, а не подтверждённое число уникальных сценариев:
есть повторы. Например, задача про падение ребёнка с велосипеда повторяется
в билете 1, задача 3, и билете 16, задача 2; массовая драка — в билете 1, задача 2,
и билете 21, задача 1. Встречаются адреса Москвы и других регионов.

[Текст билетов после OCR](<Датасет/Билеты- задачи по C 112 . АГС_ГСИ.txt>)
подготовлен для поиска. PDF состоит из сканов без текстового слоя. Распознавание
Windows.Media.Ocr (`ru`) выполнено локально; возможны ошибки цифр и смешение
колонок таблицы. Например, возраст 11 лет на первой странице распознаётся как 1.
Этот текст требует сверки с PDF перед превращением в эталоны или обучающие данные.

Ссылки ниже относятся к печатным страницам PDF; они совпадают с номерами страниц файла.
Для поиска доступен извлечённый текст.
Текст изображений не полностью представлен в этой выгрузке; важные снимки проверены отдельно.

### Границы выводов

- Памятка не задаёт учебный норматив **3 минуты**, события его начала/конца и правила
  учёта ожидания. По решению капитана эти детали определяет команда.
- На стр. 25 описаны первичные и последующие варианты выбора, но полной матрицы
  переходов между всеми этапами нет. Из неё нельзя автоматически вывести требование
  всегда проходить все этапы без пропусков.
- Отражение уточнений в комментарии подтверждено. Полной таблицы прав ДДС на изменение
  исходного адреса, типа и списка служб нет.
- Права на исходную запись в реальной системе памятка не устанавливает. Капитан
  сообщил, что аудио не предоставляют; учебная оценка строится по текстовым данным
  и собственным ошибкам ввода ученика.
- Обязательность прямого перенаправления карточки кнопкой в АРМ не установлена.
  Передача информации по телефону и добавление службы в исходную карточку —
  разные действия.
- Внутренний выбор бригады, учебные номера и конкретный обмен звонками ДДС↔бригада
  не расписаны. Источник статуса известен — полученные сведения о ходе работ;
  инициатор каждого звонка и форма имитации определяются учебным сценарием команды.
- Скриншоты памятки разных лет и ранее полученные снимки могут отличаться.
  Наличие в памятке более полного перечня статусов нужно согласовать с целевым
  учебным процессом, а не автоматически объявлять любую старую иллюстрацию актуальным UI.

### Исключения для 103 и 104

Стр. 23 устанавливает:

- 103 не использует «Не принята» и «Отказ от выполнения работ»; вместо них —
  «Работы завершены: Завершение работ без бригады».
- 104 не всегда добавляет комментарии из-за особенностей интеграции систем.

В переписке 21.09 заказчик допустил универсальный алгоритм для всех служб.
24.09 капитан подтвердил универсальный алгоритм в ответ на вопрос об этих исключениях.
Для прототипа отдельная специализация поведения 103/104 не требуется.

## Что это меняет для команды

1. Вопрос «нам не выдали билеты и памятку» закрыт. Получение источников подтверждено,
   но импорт и проверка сценариев в приложении — отдельная задача.
2. Оценку реакции нужно сверить с памяткой: **направление → первичный статус**.
   В текущем [I-TIME](../../contracts/I-TIME.md) записано **deliver → open**;
   это отличающееся правило команды, которое нельзя объявлять соответствующим памятке.
3. Модель действий должна учитывать отдельные «Прибытие» и «Проведение работ»,
   возврат «Не принята → Принята», комментарии отказа и закрытие редактирования.
   Наличие только упрощённой цепочки в прежних контрактах не закрывает эти пункты.
4. «Номер наряда» нужно учесть при сверке названий полей интерфейса.
5. Сценарии отказа можно опирать на разборы стр. 28–32 уже сейчас. Обязательное
   перенаправление каждой отвергнутой карточки и наказание за его отсутствие
   требуют отдельного предметного основания.
6. Парсер `packages/evalcore/evalcore/classifier.py` ожидает 90 колонок и фиксированные
   позиции. Новый CSV нельзя подставить в него без адаптации структуры и проверки правил.
7. Билеты содержат уточнения адреса, повторы и происшествия за пределами Москвы.
   При подготовке входных карточек нужно явно задавать, какие сведения уже известны ДДС;
   не оценивать ученика за факты, которых нет в доступных ему данных.

Эти пункты фиксируют влияние на проект. Поведение приложения и принятые контракты
в ходе анализа не изменялись.
