# Правила разработки — для людей и ИИ-агентов

> Версия 1.0, 2026-09-18. Действует для всех зон (`architecture/mvp_plan.md` §3) и для всех
> агентов (Claude Code, Cursor, свои пайплайны). Качество кода — критерий экспертизы ЛЦТ
> (ТЗ §16 «качество кода», §13 «сложные места — с комментариями», «перечень библиотек»), поэтому
> правила — не вкусовщина, а часть сдачи. Если правило мешает — меняем правило через PR, а не
> нарушаем молча. Уточнение учебного UI от 22.09 — §4 и
> план v0.3.

## 0. Три принципа

1. **Контракты — закон.** `contracts/*` (OpenAPI, WS-события, JSON-схемы карточки и сценария,
   `jobs.md`, `evalcore/README.md`) — единственный стык между зонами. Изменение контракта — PR с
   меткой `contract:` и ревью капитана; потребители обновляются в тот же день.
2. **Не угадывать.** Неясно, чего хочет контракт/скриншот/ТЗ — вопрос в чат или тикет, а не
   «сделаю как логично». Факты помечаем `[CONFIRMED] / [LIKELY] / [ASSUMPTION] / [UNKNOWN]`.
3. **Читаемо сокомандником и экспертом.** Код читает человек, который видит репо впервые:
   маленькие функции, говорящие имена, комментарий «почему» у неочевидного, README у пакета.

## 2. Структура и зоны

Карта репо — `architecture/system_design.md` §11, зоны — `architecture/mvp_plan.md` §3.
Правило: **пишем только в своей зоне.** Общие места (`contracts/`, `apps/web/src/shared/`,
`deploy/`) — через капитана (PR или тикет); `data/` и `scripts/` — зона Data Engineer в пайплайне
капитана (после дня 1 — тоже через капитана). Чужой код не рефакторим «попутно».

**Где лежат тесты:** рядом с кодом — `apps/api/tests/`, `packages/evalcore/tests/`, `apps/web`
(vitest), `scripts/tests/`. В `qa/` — только кросс-зонное: `e2e/`, `visual/`, `smoke/`, `load/`.

## 3. Python (`apps/api` — api + worker в одном пакете `app/`, `packages/evalcore`, `scripts/`)

- Python **3.12**, менеджер — **`uv`** (`uv sync`, `uv run`), `pyproject.toml` в каждом пакете, lock в git.
- Стиль: **ruff** (lint + format, длина строки 100), **mypy** (basic, без `ignore` без причины).
  `uv run ruff check . && uv run ruff format --check . && uv run mypy .` — зелёные до PR.
- Типы на всех публичных функциях. Ввод/вывод HTTP — **Pydantic v2**; `evalcore` — **dataclasses**.
- Раскладка `apps/api/app/`: `api/` (роуты), `core/` (конфиг, БД, модели, безопасность, аудит),
  `worker/` (jobs, планировщик, провайдеры), `seed/` (загрузчик `data/`), `tools/`. Два entrypoint'а
  из одного образа: `python -m app.api`, `python -m app.worker`. Отдельной папки `apps/worker/` нет.
- `api`: модуль = `router.py / service.py / schemas.py / repo.py`; чужие таблицы — только через
  сервис их модуля. Всё **async** (asyncpg); блокирующие вещи (LLM, ffmpeg, ONNX) — только в `worker`.
- HTTP-соглашения: CSRF — double-submit (cookie `csrf` + заголовок `X-CSRF-Token` на мутациях);
  ошибки — JSON `{code, message, details}`; CSV-выгрузки — UTF-8 с BOM, разделитель `;`, даты ISO-8601.
- `scripts/` — свой uv-проект (зависимость `evalcore`), пишет **только файлы** в `data/`; в БД
  загружает `python -m app.seed` (идемпотентно).
- RBAC — зависимость FastAPI на **каждом** роуте; все мутации — через audit middleware.
- Ошибки — явные: свои классы исключений → единый JSON `{code, message, details}`; исключения не
  глотаем, `None` вместо ошибки не возвращаем.
- Логи — **структурированный JSON** через `logging` + один formatter; `print` запрещён; ПДн в
  логи не пишем.
- Конфиг — только из env (`pydantic-settings`); `.env.example` актуален; секретов в git нет.
- БД: любое изменение схемы — **Alembic-миграция**; таблицы `card_events`, `audit_log`,
  `teacher_overrides`, `predictions` — append-only (никаких `UPDATE`/`DELETE`, факт в `predictions`
  дописывается в отдельные nullable-поля); `cards.current` и `card_events` — в **одной транзакции**;
  `jsonb` только для payload'ов, у которых есть JSON-схема в `contracts/`.
- `evalcore`: чистый Python — без фреймворков, ML, HTTP и БД (чисто-Python библиотеки вроде
  `spylls` и словари-данные разрешены); детерминированность (случайность — только с явным `seed`);
  каждый критерий возвращает `evidence` и `explanation` **на русском**; константы — в
  `defaults.py`; формулы — в docstring и в `docs/evalcore_formulas.md`.
- Провайдеры (LLM/эмбеддинги/TTS/STT): интерфейс в `providers/<kind>/base.py`, выбор через env
  (`AI_PROVIDER`, …), заглушка реализует тот же интерфейс и помечена `# MVP-STUB <owner>`.
  Никаких `if provider == "mock"` в бизнес-логике.
- Тесты — **pytest**: `evalcore` — unit + golden-фикстуры (`data/golden_scenarios/`), ≥ 80 %
  покрытия; `api` — на state machine (все переходы + запрещённые), идемпотентность, RBAC, отчёты.

## 4. TypeScript / React (`apps/web`)

- Node **20 LTS**, **pnpm**. TS `strict: true`; `any` запрещён (используй `unknown` + сужение).
- Стиль: **eslint + prettier**; `pnpm lint && pnpm typecheck` — зелёные до PR.
- Структура: `src/{arm,teacher,admin,shared,api-client}`; компонент — `PascalCase.tsx`, хук —
  `useXxx.ts`, стили — `Xxx.module.css`; один компонент — одна ответственность.
- API — **только через сгенерированный клиент** (`pnpm gen:api` из `contracts/openapi.*`);
  сгенерированный `src/api-client/` **коммитим** (CI проверяет, что регенерация не даёт диффа);
  руками его не правим, `fetch` в компонентах не пишем. WS — только через `shared/ws`.
- SPA живёт на базовом пути `/app/` (Vite `base`), маршруты `/app/login`, `/app/arm`, `/app/teacher`,
  `/app/admin`; в документах сокращённо `/arm`, `/teacher`, `/admin`.
- Серверное состояние — **TanStack Query**; локальное — в компонентах; глобальный стор не заводим
  без причины.
- Каждое действие обучаемого — событие с `client_event_id` (uuid v4) и `client_ts`; буфер и
  реплей при обрыве — в `shared/ws`, не в фичах.
- Цвета/шрифты/отступы — только токены из `shared/tokens.css` (сняты со скриншотов).
  Боевые поля АРМ подтверждаются снимками ДДС. Учебный выбор исполнителя и сведения при
  симуляторе телефона (T-049/T-050) явно обозначаются как учебное дополнение; их размещение
  не выдаётся за подтверждённый вид боевого ПО. Ответы 21.09
  требуют сходства карточки и реестра, цветов и конфигурации; небольшие отличия нового/второстепенного
  UI допустимы. Прежний абсолютный запрет был правилом команды. В `/teacher` и `/admin` разрешён
  один лёгкий UI-кит (выбирается один раз, фиксируется в `apps/web/README.md`).
- Клавиатура: софтфон и карточка управляются с клавиатуры; фокус видим.
- Тесты: **vitest** для логики (таймеры, state-machine софтфона, буфер WS), **playwright** для
  e2e в `qa/e2e` (Chromium + Firefox), визуальные эталоны в `qa/visual`.

## 5. Docker, поставка, скрипты

- Всё запускается **`docker compose up`** на Windows (Docker Desktop + WSL2) и Ubuntu без `make`;
  `Makefile` — удобство для Linux, каждая его цель дублирует одну compose/pnpm/uv-команду.
- Образы — фиксированные версии, без `latest`. В рантайме **нет выхода в интернет**; модели и
  справочники — на этапе сборки или явным скриптом (`scripts/*.py`, `deploy/*.sh`).
- Скрипты для АРМ класса (установка сертификата) — в двух вариантах: `.sh` и `.ps1`.
- Сиды идемпотентны (`make seed` можно гонять повторно).

## 6. Git

- Ветки: `feature/<зона>-<что>` (`feature/evalcore-address`, `feature/web-arm-card`,
  `feature/softphone`, `feature/api-cards`). В `main` — только через PR; `main` всегда зелёный.
- Мержим **каждый день**, PR маленькие (≤ 400 строк диффа по возможности). Force-push в `main` запрещён.
- Сообщение коммита: русский, повелительное наклонение, заголовок ≤ 72 символа
  (`Добавить state machine карточки и тесты переходов`). Обязательные префиксы: `contract:` —
  изменение `contracts/*` или публичного интерфейса `evalcore`; `adr:` — изменение
  `architecture/system_design.md` §9.
- В git не кладём: секреты, модели, `data/models/`, записи, бинарники > 5 МБ, `.env`, сырые логи
  сборки промптов (`agents/artifacts/agent_builder/*.{json,log,stderr}`).
  Документированное исключение для источников требований: два оригинальных DOCX в
  `docs/customer_2026-09-18/`; их происхождение и SHA-256 сохранены в
  реестре источников.
- Ничего из `docs/` не удаляем и не переименовываем.

**Чек-лист PR (DoD любой задачи):**
- [ ] линтеры и типы зелёные; тесты зелёные; CI зелёный
- [ ] в описании PR — вывод локальных проверок своей зоны (команды и итоговые строки):
      Python — `uv run pytest -q`, `uv run ruff check .`, `uv run mypy`; web — `pnpm lint`,
      `pnpm typecheck`, `pnpm test`, `pnpm build`; изменение пути в браузере — прогон
      `pnpm exec playwright test -c qa/playwright.config.ts` на поднятом стенде
      (`E2E_DATABASE=1`). С 25.09 GitHub Actions не запускаются (лимит минут), поэтому
      перед merge капитан повторяет проверки локально — без вывода PR не принимается
- [ ] контракт не изменён — или PR помечен `contract:` и потребители предупреждены
- [ ] новая зависимость обоснована одной строкой в PR, лицензия совместима (MIT/Apache/BSD/MPL;
      данные — ODbL/CC с указанием источника) — она попадёт в «перечень библиотек» для сдачи
- [ ] заглушки помечены `# MVP-STUB <owner>`; `TODO` — только с владельцем и задачей
- [ ] README пакета/зоны обновлён, если изменился запуск, конфиг или публичный интерфейс
- [ ] сложные места — с комментарием «почему»

## 7. Комментарии и документация

- Комментарий отвечает «почему», не «что». Пример хорошего: `# норматив 30 с — Q&A Q11; шкала
  кусочно-линейная, чтобы 31 с не давала 0`. Пример плохого: `# увеличиваем счётчик`.
- Docstring у каждой публичной функции `evalcore` с формулой — эксперты будут «проверять расчёты».
- У каждого пакета — `README.md`: как запустить, как тестировать, точки входа, что за что отвечает.
- Отклонение от архитектуры — ADR в `architecture/system_design.md` §9, а не комментарий в коде.

## 8. Безопасность и данные

- Запросы к БД — только через ORM/параметры; входные данные — через Pydantic/JSON-схемы.
- JWT в httpOnly-cookie + CSRF-токен; RBAC на каждом роуте; обучаемый не видит чужие результаты.
- ПДн — минимум полей, только в локальной БД; в логах, фикстурах, скриншотах и видео — только
  вымышленные ФИО/телефоны (сиды `trainee01…`, `+7 900 000-00-0N`).
- Загружаемые файлы (аудио) — проверка типа и размера, хранение вне веб-корня.

## 9. Особые правила для ИИ-агентов

- Перед любым кодом читать: свою задачу и DoD → этот файл → `contracts/` своей зоны → README пакета.
- Не выдумывать эндпоинты, поля, статусы, элементы UI. Нет в контракте/на скриншоте — нет в коде;
  нужно — тикет.
- Не трогать чужие зоны и не «улучшать попутно». Один PR — одна задача.
- Не добавлять зависимости ради удобства (`lodash` ради одной функции, `torch` ради эмбеддингов —
  используем ONNX Runtime).
- Заглушка — всегда за интерфейсом провайдера, никогда `if` в бизнес-логике.
- В отчёте о задаче: что сделано, где (пути), что **не** закрыто, что предполагалось
  (`[ASSUMPTION]`), какие тесты прогнаны — с реальным выводом, не «тесты прошли».
- Всё, что противоречит этому файлу или контрактам, — не делать молча: сообщить и остановиться.
