# Администрирование · T-016, C-07 (Dwots)

Разделы администратора в той же раскладке, что пульт преподавателя: светлая шапка,
стальная колонка разделов, тёмная полоса заголовка раздела. Заголовок
«Администрирование» проверяет e2e капитана — не менять.

| Файл                      | Ответственность                                                                  |
| ------------------------- | -------------------------------------------------------------------------------- |
| `adminModel.ts`           | чистая логика: проверка настроек, порядок весов, состояние словами               |
| `adminModel.test.ts`      | тесты этих правил, формы учётной записи и названия экрана в сообщении            |
| `AdminPage.tsx`           | раскладка и переключение разделов                                                |
| `HealthPanel.tsx`         | `GET /admin/health` и `GET /admin/status`: сводка, компоненты, нагрузка, копии   |
| `useSystemStatus.ts`      | общий опрос `/admin/status` раз в 15 с для раздела и полосы предупреждений       |
| `SettingsForm.tsx`        | `PUT /settings`: нормативы, нагрузка, подсказки, веса, потолок                   |
| `UsersPanel.tsx`          | учётные записи: список с поиском, создание, правка, пароль, блокировка, удаление |
| `BackupsPanel.tsx`        | копия по кнопке и история копий; корзина: ждут копии, обезличены, «Восстановить» |

| `ProblemReportsPanel.tsx` | `GET /problem-reports`: сообщения об ошибках, свежие сверху (28.09)              |

Стили кнопок, панелей и таблиц — из `teacher/console/Console.module.css`, раскладка —
из `teacher/TeacherPage.module.css`: один визуальный язык на все экраны зоны.

## Решения

**Настройки действуют на новые занятия.** Занятие при создании сохраняет
`settings_snapshot`, поэтому идущие занятия изменение не затрагивает. Форма говорит об
этом до сохранения, а не после.

**Проверка до отправки — по границам контракта `Settings`** и по смыслу: отработка не
короче реакции; все веса нулевыми быть не могут — итог считается как Σ(wᵢ·sᵢ)/Σwᵢ
(`packages/evalcore/evalcore/scoring.py`), делить будет не на что.
После интеграции C-01 проверяется полный набор семи числовых весов и конечность
суммы; отдельный нулевой вес и дополнительные числовые ключи сохраняются.

**Потолок при критической ошибке** описан так, как его применяет оценщик:
`min(total, critical_cap)`.

**Состояние системы словами.** Коды `Health` («worker: error») переведены в то, что
поймёт администратор класса без документации («Фоновый обработчик — не отвечает»), цвет
дублируется словом.

## Учётные записи (C-07)

Сервер: `POST /users`, `PUT /users/{id}`, `POST /users/{id}/password` — только роль `admin`,
с CSRF; логика — `apps/api/app/api/foundation/users.py`, тесты — `apps/api/tests/test_c07_users.py`.

- **Удаление — через корзину** (раздел ниже): ТЗ запрещает удалять критичные данные без
  процедуры резервного копирования, а история занятий, оценок и аудита ссылается на человека.
- **Блокировка и смена роли** отзывают серверные сессии; открытые вкладки закрываются через
  NOTIFY `user.revoked` (WebSocket 4401) во всех процессах API. Заблокированного нельзя
  добавить в занятие, и пульт преподавателя его не предлагает.
- **Себя** администратор не блокирует и роль себе не меняет — поэтому в системе всегда есть
  действующий администратор.
- **Роль** человека с учебной историей (занятия, сценарии, материалы, решения по оценкам) не
  меняется: старые отчёты остались бы ложными. Нужна новая учётная запись.
- **Логин** неизменяем: строчная латиница, цифры, `.`, `-`, `_`, 3–32 символа.
  **Пароль** — от 8 символов; интерфейс предлагает временный без похожих символов и
  показывает его один раз. Смена своего пароля оставляет текущую вкладку.

## Администратор вне учебного процесса (C-07)

ТЗ «Роль: Администратор системы»: система ограничивает администратора в прямом вмешательстве
в учебный процесс и в доступе к персональным данным без необходимости.

- `admin` убран из `x-roles` 31 учебной операции: сценарии, пакеты, занятия, выдача,
  действия по карточке, звонки, оценки и переопределения, отчёты и CSV, разборы, аудио.
  Отдельный маршрут записи звонков `/api/calls/{id}/audio` — тоже без администратора.
- WebSocket: стартовый снимок администратора пуст, учебные события ему не рассылаются.
- Кабинет преподавателя `/app/teacher` — только для роли `teacher`.
- У администратора остаются: учётки, службы, типы происшествий, настройки, состояние.
- Закреплено тестом `apps/api/tests/test_c07_admin_limits.py`: список операций в контракте,
  403 на каждой, свои инструменты — 200, пустой снимок WebSocket.

**Нормативы.** «Нормативы и оценка» у администратора — значения по умолчанию для класса
(`PUT /settings`). Тайминг и критерии успешности по ТЗ настраивает преподаватель: в форме
«Новое занятие» блок «Нормативы и оценка занятия» (те же поля — `SettingsFields`) меняет
только снимок этого занятия (`settings_snapshot`), не трогая класс и занятия коллег.

## Службы ДДС (C-07, NFR-12)

`PUT /services/{id}` `{is_active}` — только `admin`; логика — `catalog/service.py`, тесты —
`apps/api/tests/test_c07_services.py`. Справочник не удаляется, служба выключается.

- Выключенной службе нельзя позвонить и перенаправить в неё карточку (сервер уже проверял
  `is_active`), её нет в новых занятиях и пакетах: пульт и студия её не предлагают, редактор
  сценария помечает «— выключена».
- Пока служба — ДДС участника или адресат выданного сценария в **идущем** занятии, выключить
  её нельзя (409 `service_in_use` с числом занятий): это было бы вмешательство в учебный
  процесс. Включение — сразу, без подтверждения.

## Журнал аудита (C-07; ТЗ: системные журналы, аудит безопасности; FR-7.3)

`GET /audit` — только `admin`; логика — `apps/api/app/api/audit/`, тесты —
`apps/api/tests/test_c07_audit.py`. Запись делает `core/audit.py` для каждого изменяющего
запроса, включая отказы; журнал только дописывается (триггер `immutable_journal`) и
хранится бессрочно — раздел показывает самую раннюю запись.

- **Категории:** администрирование (учётки, службы, нормативы — по умолчанию), входы и
  выходы, учебный процесс, технические (замеры часов). Фильтры: результат, кто, период.
- **«Было → стало»** — только для учёток, служб и нормативов, словами. У учебных записей
  (оценки, карточки, занятия) администратор видит лишь факт действия: результаты
  обучаемых ему не раскрываются (пункт «минимальные привилегии»).
- **Неудачный вход** ссылается на учётку, в которую пытались войти, если она существует.
  Введённый текст логина не пишется: в поле логина по ошибке набирают пароль.
- Пароли и их хеши в журнал не попадают (проверено тестом).

## Состояние системы (C-07; ТЗ: компоненты в реальном времени, нагрузка, бэкап; FR-7.2, FR-7.4)

`GET /admin/status` — только `admin`, только чтение и только технические сведения; логика —
`apps/api/app/api/system/`, тесты — `apps/api/tests/test_c07_status.py`. Сводку капитана
(`/admin/health`, «всё работает») не трогаем — рядом добавлены плитки:

- канал обновлений (онлайн: людей и вкладок), очередь заданий (ждут, выполняются, с ошибкой,
  последний отклик обработчика), идущие занятия, нагрузка процессора, память, место на диске
  и размер базы, резервные копии (последняя, сколько, идёт ли копирование);
- **оповещения** собирает сервер: «сбой» (база, обработчик, канал обновлений) и «внимание»
  (копий нет или больше суток, меньше 10 % диска, задания с ошибкой, перегрузка);
- предупреждения видны полосой на **всех** страницах администрирования; сбои компонентов и так
  показывает красная плашка общей шапки (`SystemAlert`), поэтому не дублируются.

Копии: контейнер API читает папку `backup` (`${BACKUP_DIR:-../backups}:/backups:ro`,
`BACKUP_STATUS_DIR`) — копия считается готовой, когда появился каталог `backup-<время>`
(его создаёт `backup-once` после проверки сумм). Запуск и остановка сервисов из браузера не
делаются — по C-07 только документированной процедурой.

## Копии и корзина (C-07; ТЗ: резервное копирование, запрет удалять без копии)

Сервер: `POST /users/{id}/trash` `{reason}`, `POST /users/{id}/restore`, `GET /admin/trash`,
`GET/POST /admin/backups` — только `admin`, изменения с CSRF; логика —
`foundation/trash.py`, `system/backups.py`, тесты — `apps/api/tests/test_c07_trash.py`.

- **Удалить** = строка в `user_deletions` (кто, когда, причина) + блокировка + отзыв сессий;
  таблица `users` не меняется. Человек пропадает из списков
  (`GET /users` отдаёт его с `deleted_at`, чтобы отчёты и журнал находили имя). Правка и пароль
  до восстановления — 409 `user_deleted`. Себя не удаляют; пока идёт занятие с человеком
  (обучаемый или преподаватель) — 409 `user_in_training`.
- **Обезличивание** делает worker (раз в 30 с) и только для пометок раньше начала последней
  успешной копии: тогда прежние данные уже лежат в копии. Строка остаётся — на неё ссылаются
  занятия, оценки и аудит; ФИО → «Удалённый пользователь …», логин → `deleted-…` (старый
  освобождается), пароль, АРМ и служба стираются. В журнал пишется `purgeUser`.
- **Журнал не переписывается** (`immutable_journal`), но «было → стало» по обезличенному
  человеку администратору больше не показывается.
- **Восстановить** можно до обезличивания: учётка возвращается заблокированной, доступ
  открывают правкой. После — только восстановлением копии (409 `user_purged`).
- **Копия по кнопке** не выполняет команд на сервере: API пишет запрос в таблицу `backups`,
  контейнер `backup` раз в минуту забирает его (`deploy/backup/backup-poll`) и выполняет тот же
  `backup-once`, что и ночью. Ночные и консольные копии пишутся в ту же таблицу; время начала —
  по часам БД до `pg_dump`. Вторая копия, пока первая ждёт или идёт, — 409 `backup_in_progress`;
  «идущая» дольше 6 часов считается прерванной. Если журнал в БД не записался, копия всё равно
  делается, а корзина просто ждёт следующей.

## Границы

Материалы и старые занятия в корзину пока не попадают. Голосовые записи докладов удалённого
человека остаются частью истории занятия. Мёртвых кнопок не рисуем.
