# Пульт преподавателя · T-015 (Dwots)

Основной путь занятия: состав → раздача заданий → старт/завершение → ход занятия →
вердикты → отчёт. Работает против существующего HTTP-контракта, своего транспорта не
заводит: всё через `shared/api` и сгенерированный клиент.

## Раскладка

Макета пульта у заказчика нет — скриншоты есть только для АРМ. Раскладка сделана в
языке боевого АРМ (`docs/screenshots/arm_dds/02`, `07`), потому что заказчик просил
повторять цвета и конфигурацию, «чтобы решение было знакомо в первую очередь самим
преподавателям» (`docs/C08_customer_2026-09-21.md#ui-scope`). Это решение команды, а
не копия оригинала.

- **Шапка** — светлая полоса с крупным подчёркнутым заголовком, как «Поиск происшествий».
- **Слева** — стальное поле, как «Список происшествий»: занятия по группам (идут →
  черновики → завершённые, последние свёрнуты), «Новое занятие», «Студия сценариев».
  Колонка прилипает и прокручивает список сама.
- **Справа** — выбранное занятие: тёмная полоса заголовка с управлением, как
  «Происшествие 101» в карточке, и вкладки-плитки, как панель служб внизу карточки.
  Вкладка по умолчанию зависит от статуса: черновик → раздача, идёт → ход занятия,
  завершено → отчёт.

## Решения, которые стоит знать

**Служба задаётся на занятии, а не берётся из учётки.** `User.dds_service_id` только
предзаполняет строку состава; дальше преподаватель ставит любую службу и любое место.
Основание — ответ капитана 22.09 (`docs/DWOTS_REPLY_2026-09-22.md` §1); АРМ читает ту же
величину из участия.

**Уровень участника ограничивает параллельные карточки.** Планировщик берёт
`min(parallel_cards, level)`, поэтому при уровне 1 вторая карточка не придёт, сколько бы
ни стояло в настройках. В форме это написано подсказкой, чтобы не искать причину на демо.

**Сценарий уходит только своей службе.** Происшествие адресовано конкретным ДДС
(`card.service_ids`), и обучаемый за другой службой ничего с такой карточкой сделать не
может — АРМ прямо пишет «статус по ней не ставится». Поэтому раздача сопоставляет
сценарий с участником по службе, до нажатия показывает, кому сколько уйдёт, и называет
сценарий, для которого в составе нет подходящей ДДС.

**Раздача — это очередь заданий, а не одна карточка.** Отмеченные сценарии превращаются
в назначения с `order` и `planned_at`: первая карточка через N секунд, следующие с
интервалом. Интервалом преподаватель регулирует нагрузку. `order` продолжается отдельно
по каждому участнику.

**Вердикт привязан к занятию и к человеку.** У оценки нет `session_id`, поэтому связь
идёт через карточку (`Card.session_id`); в шапке вердикта — АРМ, ФИО, номер и класс
происшествия. Контракт для этого не менялся.

**Решение преподавателя фиксируется всегда.** «Согласен» отправляется тем же `POST /overrides`
с `new_total: null`, что и «не согласен» с новым баллом: заказчик требует журнал согласий,
а не только исправлений (Q&A Q3, Q13). Причина обязательна в обоих случаях,
комментарий обучаемому — отдельное поле. Форма (29.09): решение — переключателем
«Согласен с оценкой / Не согласен», для несогласия — причина и новый балл **в процентах**
(`percentToTotal`: 67 → 0,67), одна кнопка «Сохранить решение». Раньше причина и две кнопки
дублировали решение и противоречили друг другу, а балл вводился долей 0…1.

**Оценщик пока заглушка.** `status: partial` и `model_info.rules = unavailable:T-006`
показываются текстом: отсутствие оценки не выдаётся за ноль.

**CSV формирует backend** (`GET /reports/session/{id}/csv`), браузер ничего не пересчитывает.
Отказ 401/403 объясняется отдельно: cookie сессии одна на профиль браузера, поэтому вход
обучаемым в соседней вкладке незаметно забирает права у открытого пульта.

## Адресная выдача (D-01, I-SESSION)

`AddressedHandout.tsx` + `handoutModel.ts`: у каждого места своя очередь — сценарий с
версией, задержка от старта занятия, режим доставки. Уходит **одной пачкой**
`POST /sessions/{id}/assignments/batch`: всё или ничего, и никакой имитации серией
одиночных POST (так требует `contracts/C01_INTERFACES.md`).

- «Подобрать по службе и уровню» даёт каждому месту утверждённые сценарии его ДДС и
  его уровня — разные места получают разные задания.
- Сценарий чужой службы уходит только как `intentional_mismatch` и подписан
  «упражнение: чужая служба» — ошибочная доставка видна явно.
- `order` продолжает максимальный номер места среди уже выданных; задержки по
  очереди не убывают — проверяется до отправки.
- Повтор того же плана идёт с тем же `request_id` (сервер вернёт тот же ответ и не
  задвоит задания), изменённый план — с новым.
- 422 `BatchValidationError` раскладывается по строкам плана по `index`.
- C-03 отдаёт задания пачек только в `GET /sessions/{id}/assignment-batches`, в старом
  `GET /assignments` их нет. Поэтому счётчики мест, блокеры старта, нумерация новых пачек и
  очередь после старта берут всё выданное из обоих списков (`useIssuedAssignments`). Статус
  в квитанции пачки — снимок на момент выдачи, поэтому у таких заданий в очереди показаны
  задержка и режим, а не статус.
- Когда сервер пачку принимает, прежняя «Раздача по службам» скрыта: серия одиночных
  запросов пачку не заменяет.
- Доступность узнаётся чтением `GET /sessions/{id}/assignment-batches`: пока там 501,
  панель пишет, что сервер такую выдачу ещё не принимает, и работает прежняя
  «Раздача по службам». Когда капитан включит C-03, новая выдача заработает без правок.

## Отчёты (D-02)

`ReportTab.tsx` + `reportModel.ts` + `ReportCharts.tsx`. Цифры — из ответов сервера
(`GET /reports/session/{id}`, вердикты, карточки): те же, что в «Отчёт CSV»; баллы и время
в браузере не пересчитываются.

- **Попытки по стадиям:** выдано / пришло / закрыто / оценено / закрыто без оценки — у каждой
  цифры свой понятный знаменатель. Предварительные (partial) оценки объяснены словами.
- **Графики на SVG:** итоговый балл по местам и время реакции/отработки против норматива
  снимка занятия. Реакция и отработка — два графика (разные масштабы, одна ось на график).
  Место без оценки — «нет оценки», не нулевая полоса; превышение — статусным цветом и словом.
- **Причины отличий:** по месту — балл, время с отклонением от норматива, ошибки, критерии
  с просадкой (критические — отдельно).
- **Типичные ошибки группы:** частота просадки по критерию «N из M оценённых попыток».
- **Разбор человека:** попытки с объяснениями и доказательствами оценщика, комментарий
  преподавателя (его видит обучаемый), прогноз против факта в одних единицах.
- **Рекомендация сложности — правило команды, раскрытое на экране:** меньше двух оценённых
  попыток — «данных мало»; все от 80 % без критических — выше; критическая ошибка или ниже
  50 % — ниже. Подтверждение — действием: «Новое занятие с уровнем N» открывает форму с
  подставленным обучаемым и уровнем.

Ждут капитана: аналитика попыток C-06 (`/reports/session/{id}/analytics`, 501) с версией
методики времени; пустое значение в CSV для неоценённого места. См. `docs/DWOTS_FINDINGS.md`.

## Границы

- Выбранное занятие общее для нового пульта, live-доски и вердиктов.
  `LiveBoard` получает `sessionId`; переключение занятия сбрасывает локальные формы.
- `useTeacherUpdates` перечитывает HTTP-данные по WS и после snapshot; отчёт и replay
  обновляются после закрытия карточки и override. Вердикты ограничены выбранным занятием.
- «Разобрать действия» открывает `Replay` Brikkerdev. Нормативы берутся из
  `Session.settings_snapshot`, а не текущих глобальных настроек.
- CSV загружается через generated API-клиент; объяснение ошибок 401/403 сохранено.
- После частичного отказа старой последовательной раздачи назначения перечитываются:
  уже принятые сервером строки сохраняются. Атомарная пачка остаётся C-03.
- Правок и удаления участников/назначений в контракте нет (`PATCH`/`DELETE` отсутствуют) —
  не придумываем; состав задаётся при создании занятия.
- Задания принимаются только в черновике: после старта сервер отвечает 409. Поэтому после
  старта вместо выбора сценариев показана очередь выданных заданий со статусами.
- Студия сценариев (T-029) и графики отчётов (T-030) — отдельные задачи.
